Immediately after intake, status reports an `XS`–`XL` workload, estimated token range, confidence, and reasons. These are estimates, not fixed promises. At the 80% boundary SpecToPR checkpoints and continues from compact context; at the hard limit it splits scope or waits for a user decision without removing anything from `requiredValidations`.

## Use this case <span id="use-this-case-feature"></span>

Use this case to deliver a user-facing feature from a brief, Figma, and OpenAPI, then add **E2E targeting only that feature and exactly one video** to full-delivery evidence. It never records every feature or runs full-project E2E by default.

:::tip[Input / result]
**Input:** concrete user feature + `mode: feature` + UI scope · **Result:** API/UI implementation, independent functional/design reviews, targeted E2E, one video, and a draft PR
:::

## Required inputs <span id="required-inputs-feature"></span>

| Input           | Requirement                                                              |
| --------------- | ------------------------------------------------------------------------ |
| Repository      | Git repository where the browser feature and relevant checks can run     |
| `mode`          | `feature`                                                                |
| `scope`         | `ui` is required                                                         |
| `briefPath`     | PDF/Markdown acceptance criteria                                         |
| `figmaUrl`      | File/node URL for required screens and states                            |
| OpenAPI         | At least one local `openApiPaths` or HTTPS `openApiUrls` entry           |
| Feature request | State user, entry point, success/error states, and completion conditions |
| `changeKind`    | `feature`                                                                |
| `publication`   | Defaults to `draft`; use `none` to stop after reviews and local video    |

## Optional inputs <span id="optional-inputs-feature"></span>

- `docsPaths` adds business rules and edge cases.
- `guidancePaths` names project instructions such as `AGENTS.md`, architecture, and folder structure.
- `skillHints` requests applicable installed skills such as `react-best-practices`, `next-best-practices`, `design-system`, and `api-generator`.
- A Playwright test path, tag, or project can make the targeted selector unambiguous.

## What SpecToPR does <span id="process-feature"></span>

1. **Intake:** Normalize every source and feature boundary; report workload/token estimates and `requiredValidations`.
2. **Contracts:** Freeze `sourceProvenance`, requirements, API operations, and Figma `visualTargets`.
3. **API-ready:** Submit distinct non-empty type/schema/wrapper/mock files plus a passing contract-test JSON under one `implementationContextId`.
4. **UI / visual / performance:** Connect UI/API, make `apiCoverage` exactly match all intake operations, and record Web Vitals. Every actual capture repeats the target route/state/viewport/device scale/fixture and records provider, ISO capture time, PNG path, and `sha256:` digest. Runtime rejects target drift or digest mismatch without consuming an attempt before Figma/result `compare-visuals`, which requires the fixed 92%, at most 20% justified masking, and automatically runs the initial comparison plus at most two repairs. A third valid failure remains blocked with failed media; focused UI assertions remain independent.
5. **Independent reviews:** Functional and design reviewers separately judge frozen contracts, diff, and evidence.
6. **Targeted feature proof:** Run one Playwright invocation selecting the changed feature and record strict JSON plus one valid video.
7. **Report / publish:** Put source/API/visual/performance/E2E/video in packet-bound 15-section `pr-report-v2.1` and publish the draft.

Every report section is `complete`, `not-run`, `blocked`, or `not-applicable`; stale paths outside the current review packet are omitted. GitHub images, diffs, overlays, and video use immutable paths on one managed `spec-to-pr/evidence` branch and URLs pinned to the upload commit SHA, not a branch per Run.

## Execution policy: stages, agents, skills, and tools

| Durable stage       | Exact behavior for this case                                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `intake`            | Fix the user journey, UI scope, all sources, publication, workload, and `requiredValidations`.                                 |
| `contracts`         | Reconcile brief/OpenAPI/docs/Figma contracts and fix the changed-feature selector and browser evidence.                        |
| `implementation`    | One implementation writer uses one `implementationContextId`, submits API-ready before UI, and creates targeted feature proof. |
| `functional-review` | The read-only `functional-reviewer` judges contracts, diff, project checks, and targeted E2E.                                  |
| `design-review`     | The read-only `design-reviewer` judges visual, interaction, responsive, and accessibility evidence.                            |
| `report`            | Build 15-section `pr-report-v2.1` source/API/visual/Web Vitals/selector/result/video reporting.                                |
| `publish`           | Use `workflow_publish intent: ready` to sync assets and create/update a draft only.                                            |
| `archive`           | Run only after merge, authoritative evidence, and a separate request.                                                          |

Agent policy allows zero read-only scout workers for XS/S, at most one for M, and at most two for L/XL. Scouts only read sources; one implementation writer owns API and UI. There is **no nesting** and no **parallel writer**. Functional/design reviewer parallelism starts only for L/XL after implementation.

- `stageSkillRoute`: public actions route `intake-contracts` → `implement` → `review-functional`/`review-design` → `publish`. This routing is not `deliveryProfile.recommendedSkills`.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; detected React/Next packages → `react-best-practices`, `next-best-practices`; `mode: feature` + UI → `playwright` optional candidates.
- `appliedSkills`: record only the allowed union of `recommendedSkills` and actually available/applicable optional `skillHints`. Missing optional skills never weaken targeted E2E or other required evidence.
- **workflow MCP:** required. **Figma host:** required with `figmaUrl`. **Playwright Test/CLI:** required as the acceptance oracle using one changed-feature test path/tag/project command, retrying assertions, structured results, and exactly one supporting video.
- **Browser MCP:** optional interactive reproduction/inspection. **Chrome DevTools MCP:** conditional for console/network/performance/memory/live-DOM diagnosis. Neither replaces the exact Playwright selector, assertions, or positive `testCount`.

Ready and blocked drafts use the same 15-section `pr-report-v2.1`. A blocked draft exposes the stopped stage, completed work, unrun validations, and exact unblock action while remaining `status: blocked`.

### Ready, blocked diagnostic, and resume

The normal result is a video-linked draft from `workflow_publish intent: ready`. Browser evidence not run is a `BROWSER_NOT_RUN` blocker. An unresolved blocker records typed `blockerDetails` and the exact unblock action; only a clean non-target branch with supported authenticated remote, committed delta, and a one-commit lead may create a `workflow_publish intent: blocked-diagnostic` draft. It stays `status: blocked`. `PUBLISH_NO_DELTA` and other preflight failures return a **local blocked report** without empty commits or issue fallback.

For `diagnostic-publication-uncertain`, never publish automatically. Inspect GitHub/GitLab for a matching draft, show the result to the user, and call the same `workflow_publish` action with `recoverUncertain: true` only after explicit approval.

After recovery, resume the **same Run** and repeat only the failed required proof such as E2E/video. If a diagnostic draft exists, update the same source/target **same draft PR** from `[Blocked]` to the normal ready title/body and remove its blocked label.

## Evidence and validation <span id="evidence-feature"></span>

| Evidence        | Illustrative path                                 | Required condition                                                                  |
| --------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------- |
| API-ready       | `evidence/api/api-ready.json`                     | Four physical artifact roles, passing contract test, same `implementationContextId` |
| Figma           | `evidence/figma/figma-bundle.json`                | If URL supplied: real connected-host bundle and actual PNGs                         |
| Visual fidelity | `evidence/visual/checkout-report.json`            | Figma/result ratio ≥ 92%, baseline/target/diff/overlay                              |
| API gap         | `evidence/api/coverage.json`                      | Operation-level production/mock/test mapping                                        |
| Web Vitals      | `evidence/performance/checkout.json`              | Lab budget and field source or unavailable reason                                   |
| Reviews         | `evidence/reviews/functional.json`, `design.json` | Both independent verdicts approved                                                  |
| Targeted result | `evidence/e2e/targeted-feature.json`              | Only `status: passed`, exact selector, same context ID, positive `testCount`        |
| Video           | `evidence/e2e/checkout.webm`                      | `featureVideo: required`, WebM/MP4, non-zero duration, ≤25 MB, exactly one          |

The command must be one unchained Playwright invocation whose real argument selects the changed test path, tag, or project. `--list`, `--pass-with-no-tests`, broad or full-project E2E, zero tests, and zero or multiple videos are rejected.

## Expected branch and commits <span id="branch-and-commits-feature"></span>

- Illustrative branch: `codex/checkout-flow`
- Illustrative commit: `feat: add API-backed checkout flow`
- API and UI stay in one implementation agent/context rather than separate branches with an integration lane.
- Before the PR, verify the evidence video exists and the committed source branch is clean.

```md
- full-project E2E was not run
```

## When the Run stops <span id="blockers-feature"></span>

| Blocker                                                          | User action to resume                                          |
| ---------------------------------------------------------------- | -------------------------------------------------------------- |
| Source contracts conflict                                        | Choose the authoritative source and revise acceptance criteria |
| Figma URL exists but connected-host bundle is missing            | Restore host Figma access and recapture the same node          |
| API-ready artifacts, contract test, or context ID are incomplete | Resubmit physical files and passing JSON under one context ID  |
| E2E is broad, chained, list-only, skipped, or has zero tests     | Run one command selecting the changed path, tag, or project    |
| Video is absent, duplicated, invalid, or over 25 MB              | Record exactly one valid WebM/MP4 from that run                |
| Reviewer changes or dirty preflight                              | Fix, re-review, and commit only intended changes cleanly       |

## What this case does not do <span id="exclusions-feature"></span>

- It does not E2E-test or record every feature in the project.
- It does not split API and design implementation into agents and integrate later.
- It does not infer design from a Figma URL or poll Figma.
- It does not add unrelated migrations, release matrices, or full-suite evidence to a feature PR.
