Immediately after intake, status reports an `XS`–`XL` workload, estimated token range, confidence, and reasons. These are estimates, not fixed promises. At the 80% boundary SpecToPR checkpoints and continues from compact context; at the hard limit it splits scope or waits for a user decision without removing anything from `requiredValidations`.

## Use this case <span id="use-this-case-brief"></span>

Use this case for full delivery from a brief, Figma, and API documentation. It implements API and UI, measures the result against Figma, reports API usage/gaps and Web Vitals, and publishes a draft PR. Feature-targeted E2E and video are excluded.

:::tip[Input / result]
**Input:** target repository + PDF/Markdown brief + Figma URL + OpenAPI path/URL · **Result:** API/UI implementation, measured visual comparison, API gaps, Web Vitals, and a 15-section draft PR
:::

## Required inputs <span id="required-inputs-brief"></span>

| Input         | Requirement                                                                              |
| ------------- | ---------------------------------------------------------------------------------------- |
| Repository    | Absolute path to a Git repository, for example `/absolute/path/to/app`                   |
| `mode`        | `brief`                                                                                  |
| `briefPath`   | Existing regular file inside the repository, for example `docs/checkout.md`              |
| `figmaUrl`    | File/node URL for the screens and states to implement                                    |
| OpenAPI       | At least one local `openApiPaths` or HTTPS `openApiUrls` entry                           |
| Request       | Name the acceptance criteria or outcome to deliver; “implement it” alone is insufficient |
| `changeKind`  | The real kind, such as `feature`, `fix`, `refactor`, or `docs`                           |
| `publication` | `draft` for a PR or `none` for implementation and reviews only                           |

## Optional inputs <span id="optional-inputs-brief"></span>

- `scope: ui` explicitly records this case's UI contract.
- `docsPaths` adds business rules, error cases, and supporting analysis.
- `guidancePaths` points to project rules such as `AGENTS.md`, architecture, or folder structure.
- `skillHints` requests only installed and applicable skills. A missing optional skill is not a blocker.

## Minimal prompt <span id="minimal-prompt-brief"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: brief
briefPath: docs/checkout.md
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
openApiPaths: [docs/openapi.yaml]
changeKind: feature
publication: draft
Implement only the brief's acceptance criteria, run the relevant checks, and publish a draft PR.
```

## Full prompt example <span id="full-prompt-brief"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: brief
scope: ui
briefPath: docs/checkout.md
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
openApiPaths: [docs/openapi.yaml]
docsPaths: [docs/business-rules.md, docs/error-cases.md]
guidancePaths: [docs/architecture/ARCHITECTURE.md, docs/etc/folder-structure.md]
skillHints: [react-best-practices, next-best-practices, design-system, api-generator]
changeKind: feature
publication: draft
Implement only the approved checkout criteria. Stop instead of guessing if sources conflict.
Create API contract evidence first, then implement the UI in the same implementation context and run only relevant checks.
```

## What SpecToPR does <span id="process-brief"></span>

1. **Intake:** Normalize paths and publication intent; report workload, token range, and confidence.
2. **Contracts:** Freeze raw-digest `sourceProvenance`, acceptance criteria, API operations, and Figma `visualTargets`.
3. **Implementation:** Produce API types/schema/wrapper/mock/contract tests first, connect UI in the same `implementationContextId`, and map operation-complete `apiCoverage`.
4. **Visual / performance:** Every actual capture repeats the target route/state/viewport/device scale/fixture and records provider, ISO capture time, PNG path, and `sha256:` digest. Runtime rejects target drift or digest mismatch without consuming an attempt before `compare-visuals` computes exact/review ratios, diff, and overlay. It enforces the fixed 92%, no more than 20% justified masking, and automatically runs the initial comparison plus at most two repairs. A third valid failure remains blocked with failed media; focused UI assertions remain independent. Record lab metrics and field Web Vitals or an unavailable reason.
5. **Independent reviews:** `functional-reviewer` and `design-reviewer` judge the same immutable packet independently.
6. **Report / publish:** Create packet-bound `pr-report-v2.1` JSON and Markdown with 15 sections, then publish the draft.

Every report section is `complete`, `not-run`, `blocked`, or `not-applicable`; stale paths outside the current review packet are omitted. GitHub images, diffs, and overlays use immutable paths on one managed `spec-to-pr/evidence` branch and URLs pinned to the upload commit SHA, not a branch per Run.

## Execution policy: stages, agents, skills, and tools

| Durable stage       | Exact behavior for this case                                                                             |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| `intake`            | Normalize `briefPath`, request, scope, publication, workload, and `requiredValidations`.                 |
| `contracts`         | Fix the brief acceptance trace and resolve optional-source precedence or conflicts.                      |
| `implementation`    | One implementation writer works in one `implementationContextId`; API-ready precedes API-backed UI.      |
| `functional-review` | The read-only `functional-reviewer` judges contracts, diff, and focused checks from an immutable packet. |
| `design-review`     | The read-only `design-reviewer` applies only to UI scope; otherwise it is not applicable.                |
| `report`            | Build 15-section `pr-report-v2.1` source/API/visual/Web Vitals/review/risk/rollback reporting.           |
| `publish`           | Create/update a same-source/target draft only when `publication: draft` is ready.                        |
| `archive`           | Run only after merge, authoritative evidence, and a separate user request.                               |

Agent policy allows zero read-only scout workers for XS/S, at most one for M, and at most two for L/XL. Scouts only perform independent read-heavy discovery. For every UI packet, functional/design reviewers run in parallel after implementation: **no nesting** and no **parallel writer**.

- `stageSkillRoute`: public actions route `intake-contracts` → `implement` → `review-functional`, adding `review-design` for UI and `publish` for draft delivery. This routing is not `deliveryProfile.recommendedSkills`.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; detected React/Next packages → `react-best-practices`, `next-best-practices` optional candidates.
- Brief UI alone does not recommend `playwright`; only the `mode: feature` + UI mapping adds that candidate.
- `appliedSkills`: record only the allowed union of `recommendedSkills` and installed, available/applicable optional `skillHints`. Missing optional skills do not block.
- **workflow MCP:** required for Run/status/submission/publication. **Figma host:** required only when `figmaUrl` is supplied. **Playwright Test/CLI:** the assertion/structured-result oracle only when brief `requiredValidations` include browser acceptance; this profile does not inherit feature E2E or video.
- **Browser MCP:** optional interactive reproduction/inspection on capable hosts. **Chrome DevTools MCP:** conditional for console, network, performance, memory, or live-DOM diagnosis; screenshots/traces never replace assertions.

Ready and blocked drafts use the same 15-section `pr-report-v2.1`. A blocked draft exposes the stopped stage, completed work, unrun validations, and exact unblock action.

### Ready, blocked diagnostic, and resume

The normal path uses `workflow_publish intent: ready` for an evidence-backed draft. A blocker records typed `blockerDetails` and the exact unblock action. Only a valid publication preflight may use `workflow_publish intent: blocked-diagnostic`; that diagnostic draft remains `status: blocked` and is not a passed report/publish verdict. If the tree is not clean, the branch is the target, authentication/remote is unsupported, there is no committed delta or one-commit lead, or the code is `PUBLISH_NO_DELTA`, return a **local blocked report** without an empty commit or issue fallback.

For `diagnostic-publication-uncertain`, never publish automatically. Inspect GitHub/GitLab for a matching draft, show the result to the user, and call the same `workflow_publish` action with `recoverUncertain: true` only after explicit approval.

After correction, continue the **same Run** from `workflow_status`/`resumeContext` without repeating passed stages. If a diagnostic draft exists, update the same source/target **same draft PR** from `[Blocked]` to the normal `intent: ready` title/body and remove its blocked label.

## Evidence and validation <span id="evidence-brief"></span>

The paths below are an **Illustrative expectation**.

| Evidence            | Illustrative path                                            | Passing condition                                                                   |
| ------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Acceptance criteria | `evidence/contracts/brief-acceptance.json`                   | Every criterion maps to implementation and validation                               |
| API-ready           | `evidence/api/contract-test.json`                            | When API applies: passed status, physical artifacts, same `implementationContextId` |
| Focused checks      | `evidence/tests/focused-checks.json`                         | Applicable commands pass and are not skipped or empty                               |
| Figma               | `evidence/figma/figma-bundle.json`                           | When a URL exists: connected-host provenance and actual PNGs                        |
| Visual comparison   | `evidence/visual/checkout-report.json`                       | Figma/result ratios ≥ 92%, with baseline/target/diff/overlay                        |
| API gap             | `evidence/api/coverage.json`                                 | Every operation maps to production/mock/test evidence or an explicit blocker        |
| Web Vitals          | `evidence/performance/checkout.json`                         | Lab budgets plus field source or unavailable reason                                 |
| Reviews             | `evidence/reviews/functional.json`, and `design.json` for UI | Independent verdicts are approved                                                   |

Brief mode does not automatically require a targeted feature video. Validation follows the brief scope and scripts that actually exist in the repository.

## Expected branch and commits <span id="branch-and-commits-brief"></span>

- Illustrative branch: `codex/checkout-brief`
- Illustrative commit: `feat: implement checkout acceptance criteria`
- Publication requires a committed non-target source branch, intended changes only, a clean tree, and at least one commit ahead of target.
- SpecToPR never merges, approves, closes, or marks the PR ready.

## Expected draft PR <span id="expected-pr-brief"></span>

**Illustrative expectation title:** `feat: implement checkout from approved brief`

```md
## Accepted requirements

- AC-1 payment method selection → src/features/checkout/PaymentMethod.tsx
- AC-2 failure state → tests/checkout/error-state.test.tsx

## Implementation

- Added API contract and mock, then connected the UI in the same implementationContextId

## Validation and reviews

- pnpm test -- checkout: passed
- functional-reviewer: approved
- design-reviewer: approved (UI scope)

## Evidence and risks

- evidence/contracts/brief-acceptance.json
- Figma review match: 98.74% with baseline / target / diff / overlay
- API operations: 6/6 covered; gap none
- Web Vitals: LCP 2.1s, CLS 0.04, TBT 120ms
- known risks and excluded scope
```

## When the Run stops <span id="blockers-brief"></span>

| Blocker                                         | User action to resume                                                   |
| ----------------------------------------------- | ----------------------------------------------------------------------- |
| Brief, Figma, or OpenAPI is missing             | Supply all three source types or choose a different case                |
| Brief conflicts with Figma, OpenAPI, or request | Choose the authoritative source and update acceptance criteria          |
| Required project guidance is missing            | Add the file or correct `guidancePaths`                                 |
| Reviewer requests changes                       | Fix the named contract, implementation, or evidence issue and re-review |
| Dirty tree or no source commit                  | Commit only intended changes and restore a clean source branch          |

## What this case does not do <span id="exclusions-brief"></span>

- It does not invent endpoints, screens, or migrations outside the brief.
- It does not automatically add feature-only targeted E2E and one video.
- It never drops required validation because of token pressure.
