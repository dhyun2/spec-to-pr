After intake, the status shows an `XS`–`XL` workload estimate, token range, confidence, and the reasons behind the estimate. At 80% usage, SpecToPR saves a checkpoint and continues with compact context. ## Use this case <span id="use-this-case-legacy"></span>

Use this case to move behavior from a separate legacy project into the target repository. SpecToPR inventories the relevant routes, components, APIs, and state, runs both applications, and implements the behavior in the target architecture. The visual baseline is the **running legacy application**, not Figma.

:::tip[Input / result]
**Input:** target repository + separate `legacyProjectRoot` + migration scope · **Result:** source-to-target migration scope, running-legacy comparison, API Gaps, and a reviewer-first draft PR
:::

<RunPipeline locale="en" mode="legacy" />

`legacyProjectRoot` is the exact user-supplied read-only source path. SpecToPR never substitutes a similarly named directory, and OpenSpec is an optional post-merge adapter rather than a prerequisite for migration, comparison, or Draft publication.

## Required inputs <span id="required-inputs-legacy"></span>

| Input               | Requirement                                                                                                 |
| ------------------- | ----------------------------------------------------------------------------------------------------------- |
| Repository          | Absolute path to the target Git repository                                                                  |
| `mode`              | `legacy`                                                                                                    |
| `legacyProjectRoot` | Absolute path to a different read-only legacy project                                                       |
| Migration request   | “Migrate the selected scope” is enough for the whole root; name in-root routes or screens only for a subset |
| `changeKind`        | `migration`                                                                                                 |
| `scope`             | `ui`                                                                                                        |
| `publication`       | `draft` for a PR or `none` to stop after reviews                                                            |

## Optional inputs <span id="optional-inputs-legacy"></span>

- Start commands, test accounts, routes, and state for both apps help SpecToPR reproduce the same baseline quickly.
- `legacyNetworkEvidencePath`: use this only when source analysis cannot determine an HTTP method or path. Save a HAR/JSON captured from that specific flow in a gitignored evidence directory inside the target project. Standard HAR, `{requests:[{method,url}]}`, and `[{method,url}]` are accepted up to 1 MB and 1,000 requests. Raw headers, cookies, bodies, and query strings are not copied into durable artifacts or PRs. Only the file location, digest, normalized method/path, and adapter are retained.
- `briefPath`, `docsPaths`, `openApiPaths`, and `openApiUrls` add migration evidence.
- `guidancePaths` and `skillHints` specify project rules and applicable supporting skills.

## Feature scope and dependency evidence <span id="scope-and-dependencies-legacy"></span>

`legacyProjectRoot` is the **immutable feature boundary**, but dependencies needed to understand the feature may live outside that directory. Routes, screens, state, and user behavior are selected only from the root's inventory. When code inside the root directly imports or configures a dependency, SpecToPR may inspect only the HTTP client, alias configuration, environment variables, package or type declaration, and enclosing build/start configuration needed to understand and run the feature. That evidence explains the selected feature; it cannot add sibling features or justify a repository-wide keyword search. In `.env*`, only URL variables referenced by the code are considered; user info, query, and fragments are stripped before safe origins and variable names are recorded in `originRef`. Tokens, passwords, and other secrets are never persisted. Authenticated/default-client differences remain tied to their transport callsites so they can be mapped to the target project's conventions.

## Minimal prompt <span id="minimal-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy
scope: ui
legacyProjectRoot: /absolute/path/to/legacy-app
changeKind: migration
publication: draft
Migrate the selected legacy scope into the target architecture.
Run both apps, compare the same route/state/viewport, and publish the measured draft PR.
```

## Full prompt example <span id="full-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy
scope: ui
legacyProjectRoot: /absolute/path/to/legacy-app
legacyNetworkEvidencePath: evidence/legacy-network.har
docsPaths: [docs/legacy-migration-rules.md]
openApiPaths: [docs/legacy-api.yaml]
guidancePaths: [AGENTS.md, docs/architecture/ARCHITECTURE.md]
skillHints: [api-generator]
changeKind: migration
publication: draft
Inventory and migrate the selected legacy scope's routes, components, APIs, state, and persistence.
Run both projects and use the legacy screen as the visual baseline with the same fixture/viewport.
Improve the target implementation without copying the old architecture blindly.
```

## What SpecToPR does <span id="process-legacy"></span>

1. **Intake and legacy inventory:** Normalize the separate root as read-only and create a bounded `legacyInventory` of routes, components, APIs, state, persistence, bridges, and assets. The AST records only concrete HTTP requests as `apiCandidates`; constructors and local facades do not become duplicate operations. When HAR/JSON is supplied, its raw digest, the `runtime-network-har` adapter, and the observed method/path are tied to the same inventory digest. A genuinely dynamic unresolved call returns `collect-legacy-network-evidence`; submitting `legacy-network-evidence` resumes the same Run.
2. **Contracts:** Map stable keys to acceptance conditions and `planned` coverage, then declare running-legacy screenshots as `visualTargets`. Migrated files and evidence are not claimed before implementation.
3. **Implementation:** One writer moves the feature into the target architecture and replaces each planned key with current-packet migrated or excluded coverage. The legacy inventory records API candidates, environment origins, transport callsites, and confidence through semantic AST and bounded adapters such as `source-fetch-literal`, `source-http-client`, and `source-request-config`. When candidates exist, each operation needs exact `apiCoverage` and `api-ready` evidence tied to its client, mock, and test. If there are no candidates, the API section is marked `complete` and tied to the adapter list and inventory digest. An ambiguous method/path is resolved only by one unique match in scoped runtime evidence or OpenAPI. Optional OpenAPI enriches the inventory but does not decide which features are in scope.
4. **Visual comparison and performance:** Run both apps with matching route, state, fixture, and viewport. Every capture repeats the target's route/state/viewport/device scale/fixture and records its provider, ISO capture time, PNG path, and `sha256:` digest. Before `compare-visuals` runs, the runtime rejects changed comparison conditions and digest mismatches without consuming an attempt. The comparison requires the fixed 92% similarity, permits no more than 20% justified masking, and automatically runs the initial comparison and up to two repairs. A third valid failure stops automatic repair and preserves failed media as a visual-comparison Gap; focused UI assertions remain independent. Web Vitals are recorded as well.
5. **Independent reviews:** Functional and design reviewers judge migration, visuals, interaction, and accessibility.
6. **Report / publish:** Publish the Legacy migration template: source→target, migration scope, legacy visual comparison, and API Gaps, with the Gap impact and reviewer decision first.

Every report section is `complete`, `not-run`, `blocked`, or `not-applicable`. Paths from earlier review packets are omitted. GitHub images, diffs, and overlays use immutable paths on one managed `spec-to-pr/evidence` branch, with URLs pinned to the upload commit SHA instead of creating a branch for every Run.

## Execution policy: stages, agents, skills, and tools

| Durable stage       | Exact behavior for this case                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| `intake`            | Record current/desired behavior, affected entry point, scope, publication, and workload.               |
| `contracts`         | Freeze `legacyInventory`, planned coverage, running legacy `visualTargets`, and `requiredValidations`. |
| `implementation`    | One implementation writer migrates into the target architecture with API/performance evidence.         |
| `functional-review` | The read-only `functional-reviewer` judges before/after evidence and affected regressions.             |
| `design-review`     | The read-only `design-reviewer` applies only to a UI delta; otherwise it is not applicable.            |
| `report`            | Build the reviewer-first source→target, scope, visual comparison, and API Gap body.                    |
| `publish`           | Create/update a draft only when ready and `publication: draft`.                                        |
| `archive`           | Run only after verified merge and a separate user action.                                              |

Agent policy allows zero read-only scout workers for XS/S, at most one for M, and at most two for L/XL; even large legacy discovery stays independent and read-heavy. One implementation writer edits. There is **no nesting**, no **parallel writer**, and reviewers run in parallel for every UI packet after implementation.

- `stageSkillRoute`: public actions route `intake-contracts` → `implement` → `review-functional`, adding `review-design` for a UI delta and `publish` for draft delivery. This routing is not `deliveryProfile.recommendedSkills`.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; detected React/Next packages → `react-best-practices`, `next-best-practices` optional candidates.
- Legacy UI alone does not recommend `playwright`; only the `mode: feature` + UI mapping adds that candidate.
- `appliedSkills`: record only the allowed union of `recommendedSkills` and actually available/applicable optional `skillHints`. Missing optional skills never remove baseline or regression evidence.
- **workflow MCP:** required. **Figma host:** required only with `figmaUrl`. **Playwright Test/CLI:** use a focused selector and structured assertions when an affected browser regression is required; never imply full-project E2E or video.
- **Browser MCP:** optional interactive reproduction. **Chrome DevTools MCP:** conditional for console/network/performance/memory/live-DOM diagnosis, never the acceptance oracle.

### Ready, blocked diagnostic, and resume

`workflow_publish` may create a Draft when the migration has code changes even if API Gaps, failed visual comparison, or unrun review evidence remains. Such a Draft is never labelled verified or merge-ready, and `skipped` or `waived` never means passed. `PUBLISH_NO_DELTA` returns a **local report** without creating an empty commit or issue.

For `diagnostic-publication-uncertain`, never publish automatically. Inspect GitHub/GitLab for a matching draft, show the result to the user, and call the same `workflow_publish` action with `recoverUncertain: true` only after explicit approval.

After fixing the input or environment, resume the **same Run** from its latest status. If a diagnostic draft exists, update the existing draft PR for the same source and target: replace the `[Blocked]` title and body with the normal `intent: ready` content and remove the blocked label.

## Evidence and validation <span id="evidence-legacy"></span>

| Evidence   | Illustrative path                 | Passing condition                                                                           |
| ---------- | --------------------------------- | ------------------------------------------------------------------------------------------- |
| Inventory  | `contracts/legacy-inventory.json` | Stable keys and source paths are recorded                                                   |
| Coverage   | `contracts/legacy-coverage.json`  | Every scoped key is migrated/out-of-scope/gap/blocked                                       |
| Visual     | `visual/migration-report.json`    | Running legacy/result ratio ≥ 92%, mask ≤ 20%, with diff/overlay                            |
| API gap    | `evidence/api-coverage.json`      | Every derived candidate maps to production/mock/test evidence, or an empty-inventory digest |
| Web Vitals | `evidence/performance.json`       | Lab metrics plus field source or unavailable reason                                         |

These are **illustrative paths relative to `.spec-to-pr/<feature>/`**. UI or Figma sources add design evidence, but legacy mode does not automatically require a feature video.

### Where draft review material lives

When `publication: draft`, a legacy migration creates a feature-scoped review bundle at `.spec-to-pr/<feature>/`. `<feature>` normally slugifies the legacy root directory name and falls back to a stable short hash when needed, so a reviewer never has to interpret inventory keys. `publication: none` does not require this draft-only bundle.

```text
.spec-to-pr/<feature>/
├── manifest.json        # current Run/revision plus source, requirement, and OpenSpec digests
├── contracts/           # acceptance conditions and migration coverage
├── evidence/            # API, validation, and performance proof
├── visual/              # legacy/current PNGs and comparison output
└── report/              # reviewer JSON/Markdown used by the draft PR

openspec/changes/<change-name>/
├── proposal.md
├── specs/<capability>/spec.md
└── tasks.md
```

`manifest.json` binds the current Run/revision, legacy-root digest, requirement IDs, and any optionally linked OpenSpec file digests. A core Run without OpenSpec is valid; when OpenSpec is linked, only those linked files are checked for drift. The PR body leads with requirement titles, status, result files, and a **side-by-side legacy/current view**. Opaque feature keys and repetitive lists of every implementation file are hidden by default. Raw HARs, cookies, tokens, and complete logs are never copied into the bundle or PR.

### When a GitLab image upload fails

If a GitLab project upload fails because of authentication, a transient network error, or a 5xx response, verified legacy/current PNGs may use raw URLs pinned to the exact review commit. Before doing so, the runtime confirms that every image is a tracked regular file and that the exact reviewed-commit blob and clean-worktree file both match the captured SHA-256. Generated diffs and overlays, video, missing or changed files, and digest mismatches are never eligible; the report keeps the original failure instead.

## Expected branch and commits <span id="branch-and-commits-legacy"></span>

- Example branch: `codex/legacy-scope-migration`
- Example commit: `feat: migrate selected legacy scope`
- Do not mix broad formatting, dependency upgrades, or unrelated cleanup into the commit.
- Confirm a clean tree and source commit ahead of target before publication.

## Expected draft PR <span id="expected-pr-legacy"></span>

**Example title:** `feat: migrate selected legacy scope`

```md
## Legacy migration coverage

- Shop discovery and details: migrated → src/pages/shop

## Visual fidelity

- running legacy vs target review match: 98.62%
- baseline / target / diff / overlay links

## API, performance, and reviews

- documented operations: 4/4 covered; gap none
- LCP 2.2s, CLS 0.03, TBT 140ms
- functional-reviewer: approved
- design-reviewer: approved

## Risk / rollback

- no behavior outside the selected legacy scope changed
- single revertible commit
```

## When the Run stops <span id="blockers-legacy"></span>

| Blocker                                              | User action to resume                                            |
| ---------------------------------------------------- | ---------------------------------------------------------------- |
| `legacyProjectRoot` is missing or equals target      | Supply a different legacy directory                              |
| `LEGACY_API_METHOD_UNKNOWN`                          | Submit the action's scoped HAR to the same Run                   |
| HAR/JSON exceeds 1 MB/1,000 requests or is malformed | Recapture only the scoped flow in a bounded accepted format      |
| Either application cannot run                        | Supply start commands, fixtures, and environment conditions      |
| Baseline and source contract conflict                | Choose the authoritative expected behavior                       |
| Required regression cannot run                       | Provide the minimum run setup or an approved substitute artifact |
| Publication preflight fails                          | Clean and commit intended changes on the source branch           |

## What this case does not do <span id="exclusions-legacy"></span>

- It does not edit the legacy project or scan dependencies/build output without bounds.
- It does not copy old architecture blindly or damage target project guidance.
- It does not run full-project E2E or create feature video by default.
- It does not use Figma as this case's visual baseline; the running legacy app is authoritative.
