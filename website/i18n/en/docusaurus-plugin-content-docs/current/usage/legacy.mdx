Immediately after intake, status reports an `XS`–`XL` workload, estimated token range, confidence, and reasons. These are estimates, not fixed promises. At the 80% boundary SpecToPR checkpoints and continues from compact context; at the hard limit it splits scope or waits for a user decision without removing anything from `requiredValidations`.

## Use this case <span id="use-this-case-legacy"></span>

Use this case to migrate behavior from a separate legacy project into the target repository. Inventory its routes/components/APIs/state, run both applications, and implement the behavior in the target architecture. The visual baseline is the **running legacy** screen, not Figma.

:::tip[Input / result]
**Input:** target repository + separate `legacyProjectRoot` + migration scope · **Result:** legacy coverage, running legacy comparison, Web Vitals, inventory-derived API usage/gaps, and a 15-section draft PR
:::

## Required inputs <span id="required-inputs-legacy"></span>

| Input               | Requirement                                           |
| ------------------- | ----------------------------------------------------- |
| Repository          | Absolute path to the target Git repository            |
| `mode`              | `legacy`                                              |
| `legacyProjectRoot` | Absolute path to a different read-only legacy project |
| Migration scope     | Routes, screens, user behavior, and APIs to migrate   |
| `changeKind`        | `migration`                                           |
| `scope`             | `ui`                                                  |
| `publication`       | `draft` for a PR or `none` to stop after reviews      |

## Optional inputs <span id="optional-inputs-legacy"></span>

- Start commands, fixtures, route, and state for both apps make the running baseline precise.
- `legacyNetworkEvidencePath`: only when source adapters cannot determine a method/path, provide a scoped legacy-flow HAR/JSON under a gitignored evidence directory inside the target project. Standard HAR, `{requests:[{method,url}]}`, and `[{method,url}]` are accepted up to 1 MB and 1,000 requests. Raw headers/cookies/bodies/query strings are not copied into durable artifacts or PRs; only locator, digest, normalized method/path, and adapter remain.
- `briefPath`, `docsPaths`, `openApiPaths`, and `openApiUrls` add migration evidence.
- `guidancePaths` and `skillHints` specify project rules and applicable supporting skills.

## Feature scope and dependency evidence <span id="scope-and-dependencies-legacy"></span>

`legacyProjectRoot` is the **immutable feature boundary**, not a dependency visibility boundary. Select routes, screens, state, and user behavior only from that root's inventory. When in-root code directly references them through an import or configuration edge, inspect only the HTTP client, alias configuration, environment-name schema/example, package/type declaration, or enclosing build/start metadata needed to resolve and run that feature. This evidence explains an in-root feature; it does not add sibling features, and repository-wide keyword search cannot expand scope. Never read or persist actual secret values. Environment URLs remain `originRef` evidence instead of being reduced to paths, while authenticated/default client differences remain transport callsites that must map to target conventions.

## Minimal prompt <span id="minimal-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy
scope: ui
legacyProjectRoot: /absolute/path/to/legacy-app
changeKind: migration
publication: draft
Migrate the selected legacy scope into the target architecture.
Run both apps, compare the same route/state/viewport, and publish the measured draft PR.
```

## Full prompt example <span id="full-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy

guidancePaths: [AGENTS.md, docs/architecture/ARCHITECTURE.md]
skillHints: [api-generator]
changeKind: migration
publication: draft
Inventory and migrate the selected legacy scope's routes, components, APIs, state, and persistence.
Run both projects and use the legacy screen as the visual baseline with the same fixture/viewport.
Improve the target implementation without copying the old architecture blindly.
```

## What SpecToPR does <span id="process-legacy"></span>

1. **Intake / legacy inventory:** Canonicalize the separate read-only root and create bounded `legacyInventory` keys. The AST records only terminal HTTP calls as `apiCandidates`; constructors and local facades do not become duplicate operations. When HAR/JSON is supplied, pin its raw digest, the `runtime-network-har` adapter, and observed method/path into the same inventory digest. A genuinely dynamic unresolved call returns `collect-legacy-network-evidence`; submitting `legacy-network-evidence` resumes the same Run.
2. **Contracts:** Map stable keys to `planned` coverage and declare running legacy screenshots as `visualTargets`; do not claim migrated files before implementation.
3. **Implementation:** One writer migrates into the target architecture and replaces every planned key with current-packet migrated/excluded coverage. The legacy inventory records candidates, environment origins, transport/callsites, and confidence through semantic AST and bounded adapters such as `source-fetch-literal`, `source-http-client`, and `source-request-config`. Candidates require exact operation-aware `apiCoverage` and `api-ready` evidence; zero candidates produce a `complete` API section bound to the adapter list and inventory digest. Scoped runtime/OpenAPI may resolve an ambiguous method/path only when the match is unique; the Run never guesses or loses its identity. Optional OpenAPI enriches this inventory but never controls applicability.
4. **Compare / performance:** Run both apps at matching route/state/fixture/viewport. Every actual capture repeats the target route/state/viewport/device scale/fixture and records provider, ISO capture time, PNG path, and `sha256:` digest. Runtime rejects target drift or digest mismatch before `compare-visuals`, which enforces at least 98%, no more than 20% justified masking, and three total comparison attempts (the initial comparison plus at most two repairs); record Web Vitals.
5. **Independent reviews:** Functional and design reviewers judge migration, visuals, interaction, and accessibility.
6. **Report / publish:** Publish 15-section packet-bound `pr-report-v2.1` with migrated/out-of-scope/gap/blocked coverage.

Every report section is `complete`, `not-run`, `blocked`, or `not-applicable`; stale paths outside the current review packet are omitted. GitHub images, diffs, and overlays use immutable paths on one managed `spec-to-pr/evidence` branch and URLs pinned to the upload commit SHA, not a branch per Run.

## Execution policy: stages, agents, skills, and tools

| Durable stage       | Exact behavior for this case                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| `intake`            | Record current/desired behavior, affected entry point, scope, publication, and workload.               |
| `contracts`         | Freeze `legacyInventory`, planned coverage, running legacy `visualTargets`, and `requiredValidations`. |
| `implementation`    | One implementation writer migrates into the target architecture with API/performance evidence.         |
| `functional-review` | The read-only `functional-reviewer` judges before/after evidence and affected regressions.             |
| `design-review`     | The read-only `design-reviewer` applies only to a UI delta; otherwise it is not applicable.            |
| `report`            | Build 15-section `pr-report-v2.1` migration/API/visual/performance/blocker reporting.                  |
| `publish`           | Create/update a draft only when ready and `publication: draft`.                                        |
| `archive`           | Run only after verified merge and a separate user action.                                              |

Agent policy allows zero read-only scout workers for XS/S, at most one for M, and at most two for L/XL; even large legacy discovery stays independent and read-heavy. One implementation writer edits. There is **no nesting**, no **parallel writer**, and reviewer parallelism is enabled only for L/XL after implementation.

- `stageSkillRoute`: public actions route `intake-contracts` → `implement` → `review-functional`, adding `review-design` for a UI delta and `publish` for draft delivery. This routing is not `deliveryProfile.recommendedSkills`.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; detected React/Next packages → `react-best-practices`, `next-best-practices` optional candidates.
- Legacy UI alone does not recommend `playwright`; only the `mode: feature` + UI mapping adds that candidate.
- `appliedSkills`: record only the allowed union of `recommendedSkills` and actually available/applicable optional `skillHints`. Missing optional skills never remove baseline or regression evidence.
- **workflow MCP:** required. **Figma host:** required only with `figmaUrl`. **Playwright Test/CLI:** use a focused selector and structured assertions when an affected browser regression is required; never imply full-project E2E or video.
- **Browser MCP:** optional interactive reproduction. **Chrome DevTools MCP:** conditional for console/network/performance/memory/live-DOM diagnosis, never the acceptance oracle.

### Ready, blocked diagnostic, and resume

The normal path uses `workflow_publish intent: ready`. Ready and blocked use the same 15-section `pr-report-v2.1`, so a diagnostic draft exposes the stopped stage, completed migration, unrun validations, and exact unblock action. Only passing preflight may create `workflow_publish intent: blocked-diagnostic`; it remains `status: blocked`. `PUBLISH_NO_DELTA` returns a **local blocked report** without empty commits or issue fallback.

For `diagnostic-publication-uncertain`, never publish automatically. Inspect GitHub/GitLab for a matching draft, show the result to the user, and call the same `workflow_publish` action with `recoverUncertain: true` only after explicit approval.

Correct the input/environment and resume the **same Run** at its latest status. If a diagnostic draft exists, update the same source/target **same draft PR** from `[Blocked]` to the normal `intent: ready` title/body and remove the blocked label.

## Evidence and validation <span id="evidence-legacy"></span>

| Evidence   | Illustrative path                       | Passing condition                                                                           |
| ---------- | --------------------------------------- | ------------------------------------------------------------------------------------------- |
| Inventory  | `evidence/legacy/inventory.json`        | Stable keys and source paths are recorded                                                   |
| Coverage   | `evidence/legacy/coverage.json`         | Every scoped key is migrated/out-of-scope/gap/blocked                                       |
| Visual     | `evidence/visual/migration-report.json` | Running legacy/result ratio ≥ 98%, mask ≤ 20%, with diff/overlay                            |
| API gap    | `evidence/api/coverage.json`            | Every derived candidate maps to production/mock/test evidence, or an empty-inventory digest |
| Web Vitals | `evidence/performance/migration.json`   | Lab metrics plus field source or unavailable reason                                         |

Filenames are an **Illustrative expectation**. UI or Figma sources add design evidence, but legacy mode does not automatically require a feature video.

## Expected branch and commits <span id="branch-and-commits-legacy"></span>

- Illustrative branch: `codex/legacy-scope-migration`
- Illustrative commit: `feat: migrate selected legacy scope`
- Do not mix broad formatting, dependency upgrades, or unrelated cleanup into the commit.
- Confirm a clean tree and source commit ahead of target before publication.

## Expected draft PR <span id="expected-pr-legacy"></span>

**Illustrative expectation title:** `feat: migrate selected legacy scope`

```md
## Legacy migration coverage

- legacy_scope_feature: migrated → src/features/migrated-scope

## Visual fidelity

- running legacy vs target review match: 98.62%
- baseline / target / diff / overlay links

## API, performance, and reviews

- documented operations: 4/4 covered; gap none
- LCP 2.2s, CLS 0.03, TBT 140ms
- functional-reviewer: approved
- design-reviewer: approved

## Risk / rollback

- no behavior outside the selected legacy scope changed
- single revertible commit
```

## When the Run stops <span id="blockers-legacy"></span>

| Blocker                                              | User action to resume                                            |
| ---------------------------------------------------- | ---------------------------------------------------------------- |
| `legacyProjectRoot` is missing or equals target      | Supply a different legacy directory                              |
| `LEGACY_API_METHOD_UNKNOWN`                          | Submit the action's scoped HAR to the same Run                   |
| HAR/JSON exceeds 1 MB/1,000 requests or is malformed | Recapture only the scoped flow in a bounded accepted format      |
| Either application cannot run                        | Supply start commands, fixtures, and environment conditions      |
| Baseline and source contract conflict                | Choose the authoritative expected behavior                       |
| Required regression cannot run                       | Provide the minimum run setup or an approved substitute artifact |
| Publication preflight fails                          | Clean and commit intended changes on the source branch           |

## What this case does not do <span id="exclusions-legacy"></span>

- It does not edit the legacy project or scan dependencies/build output without bounds.
- It does not copy old architecture blindly or damage target project guidance.
- It does not run full-project E2E or create feature video by default.
- It does not use Figma as this case's visual baseline; the running legacy app is authoritative.
