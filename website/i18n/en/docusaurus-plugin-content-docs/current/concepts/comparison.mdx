# Spec-to-development comparison and adoption policy

This page uses only official product documentation and first-party repositories verified on **2026-07-15**. It is not a feature ranking. It explains why SpecToPR keeps seven MCP tools, eight durable stages, one implementation writer, and two read-only reviewers.

:::info[Version labels]
This guide describes the SpecToPR `0.3.0` release.
:::

## Framework comparison <span id="comparison-matrix"></span>

| [GitHub Spec Kit](https://github.github.com/spec-kit/index.html) | A Markdown artifact chain from constitution through specify, clarify, plan, checklist, and tasks              | `/speckit.implement`; large work can be bounded by task/phase, supported subagents, or smaller specs  | `analyze` before implementation and `converge` afterward                                                           | Core SDD does not own PR publication; Git and PR behavior sit at extension boundaries                               | Its workflow engine persists state and resumes at the exact paused/failed step. | [BMAD](https://docs.bmad-method.org/reference/workflow-map/)     | Quick Flow, Method, and Enterprise scale PRD, UX, architecture, epics, stories, and readiness                 | Specialist workflows implement story by story; official guidance recommends a fresh chat per workflow | PRD validation, readiness `PASS/CONCERNS/FAIL`, tests, and code review                                             | BMAD does not always create a PR. ## Adopted

- Stable contract/artifact handoff, pre-implementation consistency checks, and post-implementation evidence checks.
- Durable state and same-Run resume at a failed or blocked boundary.
- One implementation writer, workload-gated read-only scouts, and read-only reviewers after implementation.
- A least-authority publisher that only creates or updates draft PRs/MRs; humans review and merge.
- Playwright assertions and structured reports as the browser acceptance oracle.
- Redacted `blockerDetails` with an exact unblock action, keeping success separate from blocked evidence.

## Conditional

- Read-only scouts: zero for XS/S, at most one for M, at most two for L/XL, and only for independent read-heavy discovery.
- Functional/design reviewers may run in parallel only for L/XL after implementation; design review applies only to UI scope.
- Installed/applicable host skills, Browser MCP, a host browser, and Chrome DevTools MCP are used only when applicable.
- Changed-feature Playwright E2E and exactly one video apply only to the `feature` profile.

## Rejected

- New durable tools/stages for vendor concepts, nested agents, parallel writers, and API/UI handoff lanes.
- Publisher/browser reasoning agents, hidden-hook validation, and heavy permanent teams.
- An issue fallback when a draft PR cannot be created, or direct merge/approve/close/ready transitions.
- Treating warnings or a tool-generated “done” as passing required validation.
- Replacing assertions with screenshots, video, DevTools traces, or agent observation.
- Reducing `requiredValidations` because time, context, tokens, or tools are unavailable.

These choices do not claim that another product lacks useful capabilities. They record which strengths fit SpecToPR's deliberately small runtime and typed blocked/ready publication contract.
