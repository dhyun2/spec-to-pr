# Spec-to-development 비교와 채택 정책

이 페이지는 **2026-07-15**에 확인한 공식 제품 문서와 공식 저장소만 근거로 합니다. 기능 수를 겨루는 순위가 아니라, SpecToPR의 7개 MCP tool·8개 durable stage·한 명의 implementation writer·두 명의 read-only reviewer라는 경계를 왜 유지하는지 설명하는 비교입니다.

:::info[버전 표기]
이 문서는 SpecToPR `0.3.0` 릴리스를 기준으로 설명합니다.
:::

근거 세부:

- Spec Kit의 artifact 순서와 pre/post check는 [Quick Start](https://github.github.com/spec-kit/quickstart.html), exact-step resume는 [Workflows reference](https://github.github.com/spec-kit/reference/workflows.html)에 설명되어 있습니다.
- OpenSpec의 artifact 철학은 [core concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md), verify의 비차단 성격은 [commands](https://github.com/Fission-AI/OpenSpec/blob/main/docs/commands.md), dependency/strict validation은 [troubleshooting](https://github.com/Fission-AI/OpenSpec/blob/main/docs/troubleshooting.md)에 있습니다.
- Kiro의 surface별 계약은 [CLI Specs](https://kiro.dev/docs/cli/v3/specs/), optional property-based testing의 한계는 [correctness](https://kiro.dev/docs/specs/correctness/), PR 동작은 [Web Specs](https://kiro.dev/docs/web/specs/)에서 확인했습니다.
- BMAD의 track과 resume guidance는 [getting started](https://docs.bmad-method.org/tutorials/getting-started/), 사람이 검토한 뒤에만 제안되는 Quick Dev PR 경로는 [Quick fixes](https://docs.bmad-method.org/how-to/quick-fixes/)를 따릅니다.

## Adopted

- stable contract/artifact handoff, 구현 전 consistency와 구현 후 evidence validation
- failed/blocked boundary의 durable status와 same-Run resume
- 한 명의 implementation writer, workload 크기에 따른 bounded read-only scout, 구현 뒤 read-only reviewer
- 별도 least-authority publisher가 draft PR/MR만 생성·갱신하고 사람만 review/merge
- Playwright assertion과 structured report를 browser acceptance oracle로 사용
- redacted `blockerDetails`와 정확한 unblock action; 성공과 blocked evidence를 분리

## Conditional

- read-only scout: XS/S는 0명, M은 최대 1명, L/XL은 최대 2명이며 독립적인 read-heavy discovery에만 사용
- functional/design reviewer 병렬 실행은 L/XL의 implementation 뒤에만, design reviewer는 UI scope에만 사용
- installed/applicable host skill, Browser MCP, host browser, Chrome DevTools MCP는 적용 가능할 때만 사용
- 변경 기능만 고른 Playwright E2E와 video 정확히 1개는 `feature` profile에만 적용

## Rejected

- vendor 개념을 위한 새 durable tool/stage, nested agent, parallel writer, API/UI handoff lane
- publisher/browser reasoning agent, hidden hook validation, heavy permanent teams
- draft PR을 만들 수 없을 때의 issue fallback, direct merge/approve/close/ready transition
- warning이나 tool의 “done”을 required validation 통과로 취급하는 것
- screenshot·video·DevTools trace·agent observation으로 assertion을 대체하는 것
- 시간, context, token, tool 부족을 이유로 `requiredValidations`를 줄이는 것

이 선택은 다른 도구의 기능이 부족하다는 뜻이 아닙니다. 각 도구의 강점을 SpecToPR의 작은 runtime과 typed blocked/ready publication 계약 안에서 채택할 수 있는지에 대한 경계입니다.
