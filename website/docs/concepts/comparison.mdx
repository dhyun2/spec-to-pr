# 명세 기반 개발 도구 비교와 채택 원칙

이 페이지는 **2026-07-15**에 확인한 공식 제품 문서와 공식 저장소만 근거로 합니다. 기능 수를 겨루는 순위가 아닙니다. SpecToPR이 MCP 도구 7개, 실행 상태를 보존하는 단계 8개, 구현 담당자 1명, 읽기 전용 검토자 2명이라는 경계를 유지하는 이유를 설명합니다.

:::info[버전 표기]
이 문서는 현재 배포된 SpecToPR의 공개 동작을 기준으로 설명합니다.
:::

### 확인한 근거

- Spec Kit의 산출물 순서와 구현 전후 검사는 [Quick Start](https://github.github.com/spec-kit/quickstart.html), 정확한 단계 재개는 [Workflows reference](https://github.github.com/spec-kit/reference/workflows.html)에 설명되어 있습니다.
- OpenSpec의 산출물 원칙은 [core concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md), 검증이 보관을 막지 않는다는 점은 [commands](https://github.com/Fission-AI/OpenSpec/blob/main/docs/commands.md), 의존성과 엄격한 검증은 [troubleshooting](https://github.com/Fission-AI/OpenSpec/blob/main/docs/troubleshooting.md)에서 확인했습니다.
- Kiro의 환경별 계약은 [CLI Specs](https://kiro.dev/docs/cli/v3/specs/), 선택적 속성 기반 테스트의 한계는 [correctness](https://kiro.dev/docs/specs/correctness/), PR 동작은 [Web Specs](https://kiro.dev/docs/web/specs/)에 설명되어 있습니다.
- BMAD의 작업 경로와 재개 안내는 [getting started](https://docs.bmad-method.org/tutorials/getting-started/), 사람이 검토한 뒤에만 제안되는 Quick Dev PR 경로는 [Quick fixes](https://docs.bmad-method.org/how-to/quick-fixes/)를 따릅니다.

## 채택

- 안정적인 계약·산출물 전달, 구현 전 일관성 확인, 구현 후 검증 자료 확인
- 실패·차단 상태를 보존하고 같은 실행에서 재개
- 구현 담당자 한 명, 작업량에 따른 읽기 전용 조사 담당자, 구현 뒤 읽기 전용 검토자
- 최소 권한 발행자가 초안 PR/MR만 만들거나 갱신하고 사람만 검토·병합
- Playwright 검증문과 구조화 보고서를 브라우저 통과 여부의 기준으로 사용
- 민감 정보를 제거한 `blockerDetails`와 정확한 해결 방법, 성공 자료와 차단 자료의 분리

## 조건부 채택

- 읽기 전용 조사 담당자: XS/S는 0명, M은 최대 1명, L/XL은 최대 2명이며 서로 겹치지 않는 읽기 중심 탐색에만 사용
- 기능·디자인 검토의 동시 실행: 모든 UI 검토 묶음에서 구현이 끝난 뒤 함께 시작하며, 디자인 검토자는 UI 작업에만 사용
- 설치되어 있고 현재 작업에 맞는 호스트 스킬, Browser MCP, 호스트 브라우저, Chrome DevTools MCP
- 변경 기능만 고른 Playwright E2E와 영상 1개: `feature` 방식에만 적용

## 제외

- 공급자별 개념을 위한 새 상태 보존 도구·단계, 중첩 위임, 여러 구현 담당자의 동시 편집, API와 UI 사이의 별도 전달 경로
- 발행·브라우저 판단 전용 에이전트, 숨은 훅 검증, 무거운 상시 에이전트 팀
- 초안 PR을 만들 수 없을 때의 이슈 대체 발행, 직접 병합·승인·닫기·검토 준비 전환
- 경고나 도구의 “완료” 메시지를 `requiredValidations` 통과로 취급하는 것
- 스크린샷·영상·DevTools 추적 기록·에이전트 관찰로 검증문을 대신하는 것
- 시간·맥락·토큰·도구 부족을 이유로 `requiredValidations`를 줄이는 것

이 선택은 다른 도구의 기능이 부족하다는 뜻이 아닙니다. 각 도구의 강점을 SpecToPR의 작은 실행 엔진과 구조화된 정상·차단 발행 계약 안에서 안전하게 채택할 수 있는지에 대한 경계입니다.
