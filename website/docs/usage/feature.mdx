요청을 접수하면 `XS`~`XL` 예상 작업량, 토큰 범위, 신뢰도와 산정 근거를 먼저 보여 줍니다. 이 값은 확정된 약속이 아닙니다. 사용량이 80%에 이르면 진행 상태를 저장하고 간결한 맥락으로 이어갑니다. 한계에 도달해도 `requiredValidations`를 줄이지 않고, 검증 가능한 단위로 범위를 나누거나 사용자의 결정을 기다립니다.

## 이 사용법을 쓰는 경우 <span id="use-this-case-feature"></span>

기획서·Figma·OpenAPI를 바탕으로 사용자 기능의 API와 UI를 완성하고, **변경한 기능만 실행한 E2E와 영상 하나**를 초안 PR에 추가할 때 사용합니다. 전체 프로젝트 E2E나 모든 기능의 영상을 만들지는 않습니다.

:::tip[입력 / 결과]
**입력:** 구체적인 사용자 기능 + `mode: feature` + `scope: ui` · **결과:** 변경 전후 동작, 독립 기능·디자인 검토, 변경 기능 E2E, 필수 영상 1개, 화면 비교가 있는 Feature 초안 PR
:::

## 반드시 제공할 것 <span id="required-inputs-feature"></span>

| 입력          | 요구사항                                                    |
| ------------- | ----------------------------------------------------------- |
| 저장소        | 브라우저 기능과 관련 검사를 실행할 수 있는 Git 저장소       |
| `mode`        | `feature`                                                   |
| `scope`       | `ui` 필수                                                   |
| `briefPath`   | 기능 수용 조건이 있는 PDF/MD 등                             |
| `figmaUrl`    | 구현할 화면·상태의 파일/노드 URL                            |
| OpenAPI       | `openApiPaths` 또는 HTTPS `openApiUrls` 중 하나 이상        |
| 기능 요청     | 사용자, 진입점, 성공/오류 상태, 완료 조건을 구체적으로 기술 |
| `changeKind`  | `feature`                                                   |
| `publication` | 기본값은 `draft`; 구현·검토·로컬 영상까지만이면 `none`      |

## 선택 입력 <span id="optional-inputs-feature"></span>

- `docsPaths`: 비즈니스 규칙과 예외 사례를 보충합니다.
- `guidancePaths`: `AGENTS.md`, 구조 문서, 폴더 구성 문서 같은 프로젝트 규칙을 명시합니다.
- `skillHints`: `react-best-practices`, `next-best-practices`, `design-system`, `api-generator`처럼 설치되어 있고 현재 작업에 맞는 스킬을 요청합니다.
- 기능 선택자: Playwright 테스트 경로·태그·프로젝트 중 하나를 지정하면 범위 오해가 줄어듭니다.

## 최소 프롬프트 <span id="minimal-prompt-feature"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: feature
scope: ui
changeKind: feature
publication: draft
briefPath: docs/checkout.md
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
openApiPaths: [docs/openapi.yaml]
결제 기능을 API와 UI까지 구현하고 해당 결제 경로만 E2E로 검증해 영상 하나와 함께 초안 PR로 발행해줘.
```

```text
/spec-to-pr /absolute/path/to/app

```

## SpecToPR이 진행하는 과정 <span id="process-feature"></span>

1. **접수:** 모든 입력 자료와 기능 경계를 정리하고 예상 작업량·토큰 범위와 `requiredValidations`를 보여 줍니다.
2. **계약 확정:** `sourceProvenance`, 요구사항, API 작업, Figma `visualTargets`를 고정합니다.
3. **API 준비:** 확인된 실제 타입·스키마·호출 모듈·모의 응답 파일과 계약 테스트를 하나의 `implementationContextId`로 연결합니다. 메서드·body·인증·binding이 불명확하면 안전하지 않은 쓰기를 만들지 않고 **API Gap**으로 남깁니다.
4. **UI·화면 비교·성능 측정:** 같은 맥락 ID에서 UI와 확인된 API를 연결하고, Web Vitals와 Figma/결과 `compare-visuals`를 만듭니다. 각 결과 화면에는 기준과 같은 경로·상태·화면 크기·기기 배율·테스트 데이터, 자료 제공자, ISO 형식의 촬영 시각, PNG 경로, `sha256:` 해시를 기록합니다. 실행 엔진은 비교 조건이나 해시가 달라지면 시도 횟수를 소비하지 않고 거부합니다. 고정 기준은 일치율 92% 이상, 마스킹 영역 20% 이하입니다. 최초 비교와 보정 후 최대 2회를 자동으로 수행하며, 세 번째 유효 실패는 실패 이미지를 **화면 비교 Gap**으로 보존합니다. 집중 UI 검증은 전체 점수와 독립적입니다.
5. **독립 검토:** `functional-reviewer`와 `design-reviewer`가 고정된 계약, 코드 차이, 검증 자료를 각각 판정합니다.
6. **기능 검증:** 변경 기능을 선택하는 Playwright 명령 한 번으로 엄격한 JSON 결과, 유효한 영상 하나, 필요한 실제 화면·성능 결과를 수집하고 `capture-session-v1`에 기록합니다.
7. **보고서 및 발행:** Feature flow 본문에 변경 전후 동작, 회귀 검증, 필수 사용자 흐름 영상, 화면 비교와 상단 Gap을 담아 초안 PR을 발행합니다.

각 보고서 섹션은 `complete`, `not-run`, `blocked`, `not-applicable` 중 하나입니다. 현재 검토 묶음에 속하지 않는 이전 검증 자료는 PR에서 제외합니다. 초안 PR에는 Figma 기준·결과·차이 이미지와 일치율, 기능 영상을 제공합니다. GitHub용 자료는 실행마다 새 브랜치를 만들지 않고 관리 브랜치 `spec-to-pr/evidence`의 변경되지 않는 경로에 올린 뒤 업로드 커밋 SHA로 고정합니다.

## 단계와 작업 담당

| 단계                | 이 방식에서 수행하는 작업                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| `intake`            | 사용자 흐름, UI 범위, 모든 입력 자료, 발행 방식, 작업량, `requiredValidations`를 고정합니다.                  |
| `contracts`         | 기획서·OpenAPI·문서·Figma 계약을 합치고 변경 기능 선택자와 브라우저 검증 자료를 확정합니다.                   |
| `implementation`    | 한 명의 구현 담당자가 같은 `implementationContextId`에서 API 준비 후 UI를 구현하고 기능 검증 자료를 만듭니다. |
| `functional-review` | 읽기 전용 `functional-reviewer`가 계약, 코드 차이, 프로젝트 검사, 해당 기능 E2E를 판정합니다.                 |
| `design-review`     | 읽기 전용 `design-reviewer`가 화면, 상호작용, 반응형 상태, 접근성 검증 자료를 판정합니다.                     |
| `report`            | 변경 전후 동작, 회귀 검증, 사용자 흐름 영상, 화면 비교와 상단 Gap을 리뷰어 우선 본문으로 만듭니다.            |
| `publish`           | `publication: draft`이면 Gap·실패·미실행 증빙이 있어도 초안 PR/MR을 생성하거나 갱신할 수 있습니다.            |
| `archive`           | 병합 근거가 있고 사용자가 별도로 요청한 경우에만 실행합니다.                                                  |

작업량이 XS/S이면 별도 조사 담당자를 두지 않고, M이면 최대 1명, L/XL이면 최대 2명의 읽기 전용 조사 담당자를 둘 수 있습니다. 조사 담당자는 입력 자료와 코드 위치만 탐색하며, API와 UI는 한 명의 구현 담당자가 함께 편집합니다. 중첩 위임과 여러 구현 담당자의 동시 편집은 허용하지 않습니다. UI 기능·디자인 검토는 작업량과 관계없이 구현이 끝난 직후 동시에 진행하고 두 결과를 같은 packet inbox에서 함께 적용합니다.

<details>
<summary>스킬과 도구의 세부 규칙</summary>

- `stageSkillRoute`: 공개 작업은 `intake-contracts` → `implement` → `review-functional`/`review-design` → `publish` 순서로 진행합니다. 이 경로는 `deliveryProfile.recommendedSkills`와 다릅니다.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; 감지된 React/Next 패키지 → `react-best-practices`, `next-best-practices`; `mode: feature`와 UI 작업 → `playwright`
- `appliedSkills`: `recommendedSkills`와 `skillHints` 중 실제로 설치되어 있고 현재 작업에 맞는 스킬만 기록합니다. 선택 스킬이 없어도 변경 기능 E2E나 다른 필수 검증을 줄이지 않습니다.
- **워크플로 도구:** 필수입니다. **Figma 호스트 기능:** `figmaUrl`이 있을 때 필수입니다. **Playwright Test/CLI:** 변경 기능을 테스트 경로·태그·프로젝트로 고른 단일 명령, 재시도 가능한 검증, 구조화 결과의 판정 기준으로 사용합니다. 영상은 보조 자료로 정확히 1개만 남깁니다.
- **Browser MCP:** 상호작용을 재현하고 살펴볼 때 선택적으로 사용합니다. **Chrome DevTools MCP:** 콘솔·네트워크·성능·메모리·실시간 DOM 문제를 진단할 때만 사용합니다. 두 도구 모두 Playwright 검증, 양수인 `testCount`, 정확한 선택자를 대신하지 않습니다.

</details>

기계용 보고서는 증거를 보존하지만, Draft PR 본문은 변경 전후 동작, 회귀 검증, 정확히 하나의 사용자 흐름 영상, 화면 비교와 상단 Gap만 보여 줍니다. Gap·실패·미실행·`skipped`·`waived`가 있으면 verified나 merge-ready로 표시하지 않습니다.

### 정상 발행, 차단 진단, 재개

`workflow_publish`는 코드 변경과 발행 사전 조건이 있으면 영상·브라우저 검증·화면 비교가 미실행이거나 실패한 경우에도 Draft를 만들 수 있습니다. Feature flow의 영상은 여전히 필수 증거이므로 없으면 `BROWSER_NOT_RUN` Gap의 영향과 리뷰어 결정을 상단에 표시하며 verified나 merge-ready가 아닙니다. `PUBLISH_NO_DELTA` 같은 사전 검사 실패가 발생하면 빈 커밋이나 대체 이슈를 만들지 않고 **로컬 보고서**를 반환합니다.

`diagnostic-publication-uncertain`이면 자동으로 다시 발행하지 않습니다. GitHub/GitLab에서 소스와 대상 브랜치가 같은 기존 초안을 확인해 사용자에게 보여 주고, 명시적인 승인을 받은 경우에만 같은 `workflow_publish`를 `recoverUncertain: true`로 호출합니다.

문제를 해결한 뒤에는 최신 상태의 **같은 실행**을 재개하고 E2E·영상처럼 실패한 필수 작업만 다시 검증합니다. 진단용 초안이 있었다면 소스와 대상 브랜치가 같은 **기존 초안 PR**의 `[Blocked]` 제목·본문을 정상 발행 내용으로 바꾸고 차단 라벨을 제거합니다.

## 검증 자료와 통과 기준 <span id="evidence-feature"></span>

| 검증 자료        | 예상 예시                                         | 필수 조건                                                                      |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------------------------ |
| API 준비         | `evidence/api/api-ready.json`                     | 서로 다른 실제 파일 4종, 통과한 계약 테스트, 같은 `implementationContextId`    |
| Figma            | `evidence/figma/figma-bundle.json`                | URL을 제공했다면 연결된 호스트의 실제 자료 묶음과 PNG                          |
| 화면 일치        | `evidence/visual/checkout-report.json`            | 검토 일치율 92% 이상, 기준·결과·차이·겹침 이미지                               |
| API 현황         | `evidence/api/coverage.json`                      | API 작업별 실제 호출·모의 응답·테스트 연결                                     |
| Web Vitals       | `evidence/performance/checkout.json`              | 실험실 기준과 현장 자료 또는 수집하지 못한 이유                                |
| 기능·디자인 검토 | `evidence/reviews/functional.json`, `design.json` | 두 독립 판정이 모두 승인됨                                                     |
| 기능 검사 결과   | `evidence/e2e/targeted-feature.json`              | `status: passed`, 정확한 선택자, 같은 맥락 ID, 양수인 `testCount`만 포함       |
| 영상             | `evidence/e2e/checkout.webm`                      | `featureVideo: required`, WebM/MP4, 재생 시간 0초 초과, 25 MB 이하, 정확히 1개 |

허용되는 E2E는 변경 기능을 실제로 고르는 테스트 경로·태그·프로젝트를 인자로 쓰는 **연결되지 않은 Playwright 명령 한 번**입니다. 이 한 번의 호출이 필요한 feature E2E, 정확히 하나의 영상, 실제 화면·성능 결과를 함께 수집해 `capture-session-v1` 후보 매니페스트에 고정합니다. 이후 `compare-visuals`는 이미 검증된 캡처를 현재 packet 영수증으로만 만들며 Playwright를 재실행하지 않습니다. `--list`, `--pass-with-no-tests`, 범위가 넓거나 전체 프로젝트를 대상으로 한 E2E, 테스트 0건, 영상 0개나 2개 이상은 거부됩니다.

## 예상 브랜치와 커밋 <span id="branch-and-commits-feature"></span>

- 브랜치 예상 예시: `codex/checkout-flow`
- 커밋 예상 예시: `feat: add API-backed checkout flow`
- API와 UI를 별도 담당자나 브랜치로 나누지 않고 하나의 구현 맥락에서 진행합니다.
- PR 발행 전에는 영상을 포함한 검증 자료 경로가 존재하고 소스 브랜치가 커밋된 깨끗한 상태인지 확인합니다.

## 예상 초안 PR <span id="expected-pr-feature"></span>

**예상 예시 제목:** `feat: add API-backed checkout flow`

```md
## 요구사항 추적

- 기획서 AC-1..AC-5, Figma 노드 12:345, 결제 OpenAPI 작업

## API와 UI 구현

- api-ready: evidence/api/api-ready.json
- implementationContextId: checkout-20260714
- 로딩 / 오류 / 성공 UI와 실제 클라이언트 연결

## 독립 검토

- functional-reviewer: approved
- design-reviewer: approved

## 변경 기능 검증 자료

- selector: tests/e2e/checkout.spec.ts
- command: pnpm playwright test tests/e2e/checkout.spec.ts
- result: evidence/e2e/targeted-feature.json
- featureVideo: evidence/e2e/checkout.webm (1개)

## 화면, API, 성능

- Figma 검토 일치율: 99.03%
- API 작업: 6/6 검증, 누락 없음
- Web Vitals: LCP 2.0s, CLS 0.03, TBT 110ms

## 위험과 제외 범위

- 전체 프로젝트 E2E는 실행하지 않음
```

## 실행이 멈추는 경우 <span id="blockers-feature"></span>

| 중단 원인                                     | 사용자가 할 일                                          |
| --------------------------------------------- | ------------------------------------------------------- |
| 입력 자료 사이 계약 충돌                      | 우선할 자료와 수정한 수용 조건을 결정                   |
| Figma URL은 있지만 실제 자료 묶음이 없음      | 호스트 Figma 연결·권한을 복구하고 같은 노드를 다시 캡처 |
| API 준비 파일·계약 테스트·맥락 ID가 불완전함  | 실제 파일과 통과한 JSON을 같은 맥락 ID로 다시 제출      |
| E2E 범위가 넓거나 연결·목록·건너뛰기·0건임    | 변경 기능만 고르는 경로·태그·프로젝트로 단일 명령 실행  |
| 영상이 0개·여러 개·손상·25 MB 초과            | 해당 실행의 유효한 WebM/MP4 하나만 다시 기록            |
| 검토자가 수정을 요청했거나 사전 상태가 불결함 | 지적을 수정·재검토하고 의도한 변경만 깨끗하게 커밋      |

## 이 사용법이 하지 않는 것 <span id="exclusions-feature"></span>

- 전체 프로젝트의 모든 기능을 E2E로 실행하거나 영상으로 기록하지 않습니다.
- API 담당자와 디자인 담당자를 따로 만들어 나중에 합치지 않습니다.
- Figma URL만 보고 디자인을 추측하거나 상태를 반복 조회하지 않습니다.
- 관련 없는 이관, 테스트 조합, 릴리스 검증을 기능 PR에 추가하지 않습니다.
