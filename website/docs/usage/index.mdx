모든 요청은 아래 세 정보를 공통으로 사용합니다.

```yaml
case: brief | feature | figma | legacy
projectRoot: /absolute/path/to/project
request: 구현할 사용자 기능
test: on | off # brief·feature만, 생략하면 off
```

`brief`, `figma`, `legacy`는 각각 기획서 경로, Figma URL, 별도 레거시 프로젝트 경로가 추가로 필요합니다. 대상 브랜치를 지정하지 않으면 대상 프로젝트의 기본 브랜치를 사용합니다.

| 케이스               | 언제 쓰나요?               | 구현 전 준비                 | 화면 기준                   |
| -------------------- | -------------------------- | ---------------------------- | --------------------------- |
| [brief](./brief)     | 기획서로 기능을 만들 때    | OpenSpec 문서 작성·자료 대조 | 제공된 Figma 또는 승인 화면 |
| [feature](./feature) | 기능 하나를 빠르게 만들 때 | OpenSpec 문서 작성·자료 대조 | 제공된 Figma가 있을 때만    |
| [figma](./figma)     | Figma를 화면으로 옮길 때   | 선택한 Figma 화면·상태       | Figma 캡처                  |
| [legacy](./legacy)   | 별도 프로젝트를 이관할 때  | 레거시 동작·화면·API         | 실행 중인 레거시 화면       |

## case별 Draft PR 형식

하나의 범용 본문을 쓰지 않습니다. case별로 리뷰어가 바로 판단할 내용을 고릅니다.

| case      | PR 핵심 내용                                                       |
| --------- | ------------------------------------------------------------------ |
| `legacy`  | 원본→대상, 전체 route/state 화면 매트릭스, 기준·이관·Diff, API Gap |
| `brief`   | 요구사항 충족, 제외 범위, 화면 비교                                |
| `feature` | 사용자 흐름 영상, 변경 전후 동작, 회귀 검증, 화면 비교             |
| `figma`   | Figma 상태 매핑, 상태별 일치율, 디자인·접근성 검증                 |

내부 로그·실행 식별자·비어 있는 체크리스트는 빼고, Gap에는 영향과 리뷰어가 결정할 다음 작업을 씁니다. `feature` 영상은 화면 비교나 테스트를 대신하지 않습니다.

## OpenSpec과 테스트 선택

OpenSpec은 사용자가 준비해야 하는 전제 조건이 아닙니다. `brief`와 `feature`에서 저장소 규칙이나 요청 범위에 유용하면 에이전트가 준비합니다. `test: on`이면 확정된 수용 시나리오를 실패 테스트로 먼저 만들고 구현·통과·리팩터링하는 TDD를 합니다. `test: off` 또는 생략이면 이 작업을 위한 단위·통합 테스트를 만들거나 실행하지 않습니다.

`feature`의 변경 기능 E2E와 사용자 흐름 영상은 `test`와 별개인 PR 증빙입니다. `figma`와 `legacy`는 OpenSpec·TDD 모드를 적용하지 않고 각 화면·동작을 직접 기준으로 사용합니다.

각 케이스 가이드에는 그 케이스에 맞는 PR 예시가 있습니다. UI 기준이 없거나 비교가 실패해도 구현을 숨기지 않습니다. 조건과 영향, 다음 작업을 Gap에 남겨 리뷰어가 바로 판단할 수 있게 합니다. Legacy는 지정한 모든 사용자 노출 route/state가 비교 또는 명시적 제외여야 합니다.
