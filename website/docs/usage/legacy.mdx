Intake 직후 `XS`~`XL` workload, 예상 token range, confidence와 근거가 표시됩니다. 이는 고정 약속이 아닙니다. 80% 경계에서는 checkpoint와 compact context로 이어가며, 한계에 도달해도 `requiredValidations`를 빼지 않고 범위를 나누거나 사용자의 결정을 기다립니다.

## 이 케이스를 쓰는 경우 <span id="use-this-case-legacy"></span>

별도 레거시 프로젝트를 읽고 실행해 기능을 현재 대상 프로젝트로 이관할 때 사용합니다. 이전 코드를 그대로 복사하는 것이 아니라, 레거시의 동작·API·상태·화면을 inventory로 고정한 뒤 대상 구조에 맞게 더 낫게 구현합니다. 화면 일치율의 baseline은 Figma가 아니라 **running legacy 화면**입니다.

:::tip[입력 / 결과]
**입력:** 대상 저장소 + 별도 `legacyProjectRoot` + 이관 범위 · **결과:** migration coverage, running legacy 대비 화면 비교, Web Vitals, inventory에서 파생한 API 사용/gap, 15개 섹션 draft PR
:::

## 반드시 제공할 것 <span id="required-inputs-legacy"></span>

| 입력                | 요구사항                                             |
| ------------------- | ---------------------------------------------------- |
| 대상 저장소         | 새 구현과 PR이 만들어질 Git 저장소 절대 경로         |
| `mode`              | `legacy`                                             |
| `legacyProjectRoot` | 대상과 다른 레거시 프로젝트의 절대 경로              |
| 이관 범위           | route, 화면, 사용자 동작, 관련 API를 구체적으로 기술 |
| `changeKind`        | `migration`                                          |
| `scope`             | `ui`                                                 |
| `publication`       | PR이면 `draft`, 발행하지 않으면 `none`               |

## 선택 입력 <span id="optional-inputs-legacy"></span>

- 두 프로젝트의 실행 명령, fixture 계정, route/state: running baseline을 빠르게 고정합니다.
- `legacyNetworkEvidencePath`: source adapter가 method/path를 확정하지 못할 때만 대상 프로젝트 내부의 gitignore된 evidence 디렉터리에 저장한 scoped legacy flow HAR/JSON을 제공합니다. 표준 HAR, `{requests:[{method,url}]}`, `[{method,url}]` 형식을 최대 1 MB·1,000 request까지 받습니다. 원문 header/cookie/body/query는 durable artifact/PR에 복사하지 않고 locator·digest·정규화한 method/path·adapter만 남깁니다.
- `briefPath`, `docsPaths`, `openApiPaths`, `openApiUrls`: 이관 범위의 추가 계약 근거입니다.
- `guidancePaths`, `skillHints`: 프로젝트 규칙과 적용 가능한 보조 skill을 명시합니다.

## 최소 프롬프트 <span id="minimal-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy
scope: ui
legacyProjectRoot: /absolute/path/to/legacy-app
changeKind: migration
publication: draft
지정한 레거시 범위 전체를 대상 프로젝트 구조에 맞게 이관해줘.
레거시와 결과를 같은 route/state/viewport로 실행해 화면 일치율까지 비교하고 draft PR로 발행해줘.
```

## 전체 프롬프트 예시 <span id="full-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy
scope: ui
legacyProjectRoot: /absolute/path/to/legacy-app
legacyNetworkEvidencePath: evidence/legacy-network.har
docsPaths: [docs/legacy-migration-rules.md]
openApiPaths: [docs/legacy-api.yaml]
guidancePaths: [AGENTS.md, docs/architecture/ARCHITECTURE.md]
skillHints: [api-generator]
changeKind: migration
publication: draft
지정한 레거시 범위의 route, component, API, state, persistence를 inventory로 고정하고 대상 프로젝트로 이관해줘.
두 앱을 실행해 레거시 화면을 visual baseline으로 사용하고 같은 fixture/viewport의 결과와 비교해.
이전 코드를 복사하지 말고 대상 architecture와 guidance에 맞게 개선하되 사용자 동작은 보존해.
```

## SpecToPR이 진행하는 과정 <span id="process-legacy"></span>

1. **Intake / legacy inventory:** 별도 root를 read-only로 정규화하고 route/component/API/state/persistence/bridge/asset 등을 bounded `legacyInventory`로 만듭니다. 선택 HAR/JSON을 주면 raw digest, `runtime-network-har` adapter, 관측된 method/path를 같은 inventory digest에 고정합니다. Intake가 blocked이면 `nextActions`는 비어 있고 downstream submission도 거부됩니다.
2. **Contracts:** stable feature key를 수용 조건과 `planned` coverage로 연결하고 running legacy screenshot을 `visualTargets`로 고정합니다. 구현 전에는 migrated 파일이나 증거를 주장하지 않습니다.
3. **Implementation:** 한 implementation writer가 대상 프로젝트 규칙에 맞게 이관하고 같은 stable key를 current-packet `migrated`/제외 coverage로 교체합니다. Legacy inventory는 `source-fetch-literal`, `source-fetch-dynamic`, `source-http-client`, `source-request-config`, `source-generated-client` bounded adapter로 API 후보와 confidence를 기록합니다. 후보가 있으면 operation별 client/mock/test와 정확히 일치하는 `apiCoverage`/`api-ready` 증거를 요구하고, 후보가 0개면 API 섹션을 adapter 목록과 inventory digest에 묶어 `complete`로 기록합니다. Method/path가 모호한 request는 추측하지 않으며, scoped runtime/OpenAPI가 유일하게 확정하면 병합하고 그렇지 않으면 `LEGACY_API_METHOD_UNKNOWN` durable intake blocker로 반환합니다. 선택 OpenAPI는 이 inventory를 보강하지만 적용 여부를 결정하지 않습니다.
4. **Compare / performance:** 두 앱을 같은 route/state/fixture/viewport로 실행합니다. 각 actual capture는 target의 route/state/viewport/device scale/fixture를 반복하고 provider, ISO capture time, PNG path, `sha256:` digest를 기록합니다. `compare-visuals`는 target drift·digest mismatch를 거부하고 exact/review ratio, diff, overlay를 계산합니다. 런타임 기준은 최소 98%, 정당한 mask 최대 20%, 비교 총 3회(최초 1회 + repair 최대 2회)입니다. Web Vitals도 측정합니다.
5. **Independent reviews:** functional과 design reviewer가 migration coverage, 화면, interaction, accessibility를 독립 판정합니다.
6. **Report / publish:** `pr-report-v2.1` 15개 섹션으로 migrated/out-of-scope/gap/blocked와 rollback을 공개하고 draft PR을 만듭니다.

각 보고서 섹션은 `complete`, `not-run`, `blocked`, `not-applicable` 중 하나입니다. 현재 review packet에 속하지 않는 stale path는 PR에서 생략합니다. GitHub 이미지·diff·overlay는 실행별 branch가 아니라 단일 관리 branch `spec-to-pr/evidence`의 immutable 경로에 올리고 upload commit SHA로 고정합니다.

## 실행 정책: stage, agent, skill, tool

| Durable stage       | 이 케이스의 정확한 동작                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| `intake`            | current/desired behavior, affected entry point, scope, publication과 workload를 기록합니다.              |
| `contracts`         | `legacyInventory`, planned coverage, running legacy `visualTargets`, `requiredValidations`를 확정합니다. |
| `implementation`    | 한 writer가 이관하고 current-packet migrated/excluded coverage와 파생 API/performance 증거를 만듭니다.   |
| `functional-review` | read-only `functional-reviewer`가 before/after evidence와 affected regression을 판정합니다.              |
| `design-review`     | UI delta일 때만 read-only `design-reviewer`가 적용되고 non-UI면 not applicable입니다.                    |
| `report`            | `pr-report-v2.1` 15개 섹션에 migration/API/visual/performance gap과 blocker를 기록합니다.                |
| `publish`           | ready이고 `publication: draft`일 때만 draft PR/MR을 생성·갱신합니다.                                     |
| `archive`           | merge가 확인된 뒤 별도 사용자 action으로만 실행합니다.                                                   |

Agent 정책은 XS/S read-only scout 0명, M 최대 1명, L/XL 최대 2명이며 큰 legacy discovery도 독립적인 read-heavy 범위로 제한합니다. 한 implementation writer만 편집하고 **no nesting**, **parallel writer 금지**입니다. Reviewer 병렬 실행은 implementation 뒤 UI scope인 L/XL에서만 켜집니다.

- `stageSkillRoute`: public action은 `intake-contracts` → `implement` → `review-functional` 순서이며 UI delta면 `review-design`, draft면 `publish`로 이어집니다. 이 routing은 `deliveryProfile.recommendedSkills`가 아닙니다.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths`/`openApiUrls` → `api-generator`; 감지된 React/Next package → `react-best-practices`, `next-best-practices` optional candidate입니다.
- Legacy UI라는 이유만으로 `playwright`를 추천하지 않습니다. `mode: feature` + UI mapping만 해당 candidate를 추가합니다.
- `appliedSkills`: `recommendedSkills`와 실제 available/applicable한 `skillHints`의 optional-skill 허용 합집합만 기록합니다. Missing optional skills로 baseline이나 필수 회귀 검증을 생략하지 않습니다.
- **workflow MCP:** durable Run에 필수. **Figma host:** `figmaUrl`이 있을 때만 필수. **Playwright Test/CLI:** affected browser regression이 required일 때 focused selector와 structured assertion을 사용하며 full-project E2E나 영상은 요구하지 않습니다.
- **Browser MCP:** optional interactive reproduction. **Chrome DevTools MCP:** console/network/performance/memory/live-DOM 원인 진단에만 conditional이며 acceptance oracle가 아닙니다.

### Ready, blocked diagnostic, resume

정상 경로는 `workflow_publish intent: ready`로 evidence-backed draft를 만듭니다. `pr-report-v2.1`의 동일한 15개 섹션을 blocked에도 사용하므로 멈춘 stage, 완료된 migration, 미실행 검증, exact unblock action이 PR에 남습니다. Preflight를 통과할 때만 `workflow_publish intent: blocked-diagnostic` draft를 내며 결과는 계속 `status: blocked`입니다. Clean tree, non-target branch, 인증, 지원 remote, committed delta, target보다 한 commit ahead가 없거나 `PUBLISH_NO_DELTA`면 empty commit과 issue fallback 없이 **local blocked report**만 반환합니다.

`diagnostic-publication-uncertain`이면 자동 재발행하지 않습니다. GitHub/GitLab에서 matching draft를 확인해 사용자에게 보여주고, 명시적 승인을 받은 경우에만 같은 `workflow_publish`를 `recoverUncertain: true`로 호출합니다.

입력·환경을 고친 뒤 **same Run**의 latest status에서 재개합니다. Diagnostic draft가 있었다면 같은 source/target의 **same draft PR**을 `[Blocked]`에서 정상 `intent: ready` 제목/본문으로 갱신하고 blocked label을 제거합니다.

## 증거와 검증 <span id="evidence-legacy"></span>

| 증거       | 예상 예시                               | 통과 기준                                                            |
| ---------- | --------------------------------------- | -------------------------------------------------------------------- |
| inventory  | `evidence/legacy/inventory.json`        | stable feature key와 source path가 기록됨                            |
| coverage   | `evidence/legacy/coverage.json`         | 모든 scope key가 migrated/out-of-scope/gap/blocked 중 하나           |
| visual     | `evidence/visual/migration-report.json` | running legacy/결과 ratio ≥ 98%, mask ≤ 20%, diff/overlay            |
| API gap    | `evidence/api/coverage.json`            | 파생 후보 전체의 production/mock/test 매핑, 또는 빈 inventory digest |
| Web Vitals | `evidence/performance/migration.json`   | lab metrics와 field source/미가용 사유                               |

파일명은 **예상 예시**입니다. Figma 또는 UI source가 있다면 별도 design evidence가 추가되지만 기능 개발용 영상은 자동 요구하지 않습니다.

## 예상 브랜치와 커밋 <span id="branch-and-commits-legacy"></span>

- 브랜치 예상 예시: `codex/legacy-scope-migration`
- 커밋 예상 예시: `feat: migrate selected legacy scope`
- 큰 formatting, dependency upgrade, unrelated cleanup은 같은 커밋에 섞지 않습니다.
- 발행 전에 clean tree와 target보다 앞선 source commit을 확인합니다.

## 예상 Draft PR <span id="expected-pr-legacy"></span>

**예상 예시 제목:** `feat: migrate selected legacy scope`

```md
## Legacy migration coverage

- legacy_scope_feature: migrated → src/features/migrated-scope

## Visual fidelity

- running legacy vs target: review match 98.62%
- baseline / target / diff / overlay links

## API, performance, reviews

- documented API operations: 4/4 covered, gap none
- LCP 2.2s, CLS 0.03, TBT 140ms
- functional-reviewer: approved
- design-reviewer: approved

## Risk / rollback

- 지정한 레거시 범위 외 동작은 변경하지 않음
- revert 가능한 단일 커밋
```

## Run이 멈추는 경우 <span id="blockers-legacy"></span>

| 중단 원인                                           | 사용자가 할 일                                       |
| --------------------------------------------------- | ---------------------------------------------------- |
| `legacyProjectRoot`가 없거나 대상과 같음            | 별도 레거시 디렉터리 절대 경로 제공                  |
| `LEGACY_API_METHOD_UNKNOWN`                         | scoped OpenAPI 또는 `legacyNetworkEvidencePath` 제공 |
| HAR/JSON이 1 MB·1,000 request 한도/형식을 위반      | 해당 flow만 다시 캡처해 bounded 형식으로 저장        |
| 레거시/대상 앱을 실행할 수 없음                     | 실행 명령, fixture, 환경 조건 제공                   |
| baseline과 source가 충돌                            | 기대 동작의 authoritative source를 선택              |
| 검사 환경이 없어 required regression을 만들 수 없음 | 최소 실행 방법이나 승인된 대체 증거 제공             |
| publication preflight 실패                          | 변경을 정리·커밋해 clean source branch로 재개        |

## 이 케이스가 하지 않는 것 <span id="exclusions-legacy"></span>

- dependency/build output을 무제한 스캔하거나 레거시 저장소를 편집하지 않습니다.
- 이전 코드를 무조건 복사하거나 현재 대상 architecture를 훼손하지 않습니다.
- full-project E2E나 기능 영상을 자동 요구하지 않습니다.
- Figma를 visual baseline으로 사용하지 않습니다. 이 케이스의 baseline은 running legacy입니다.
