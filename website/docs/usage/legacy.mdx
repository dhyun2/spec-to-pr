요청을 접수하면 예상 작업량(`XS`~`XL`), 토큰 범위, 신뢰도와 산정 근거를 바로 보여 줍니다. 이 값은 확정된 약속이 아니라 현재 정보에 따른 예상치입니다. 사용량이 80%에 이르면 진행 상태를 저장하고 간결한 맥락으로 이어갑니다. 한계에 도달하더라도 `requiredValidations`를 줄이지 않고, 검증 가능한 단위로 범위를 나누거나 사용자의 결정을 기다립니다.

## 이 케이스를 쓰는 경우 <span id="use-this-case-legacy"></span>

별도의 레거시 프로젝트를 분석하고 실행해 기능을 현재 프로젝트로 옮길 때 사용합니다. 이전 코드를 그대로 복사하지 않습니다. 레거시의 동작·API·상태·화면을 목록으로 확정한 다음, 사용자 경험은 유지하면서 대상 프로젝트의 구조와 규칙에 맞게 구현합니다. 화면 일치율은 Figma가 아니라 **실제로 실행한 레거시 화면**을 기준으로 계산합니다.

:::tip[입력 / 결과]
**입력:** 대상 저장소 + 별도 `legacyProjectRoot` + 이관 범위 · **결과:** 원본→대상 이관 범위, 실행한 레거시와의 화면 비교, API Gap, reviewer-first 초안 PR
:::

<RunPipeline locale="ko" mode="legacy" />

`legacyProjectRoot`는 사용자가 지정한 정확한 읽기 전용 원본 경로입니다. 이름이 비슷한 폴더로
바꾸지 않으며, OpenSpec은 이관·화면 비교·Draft를 막지 않는 선택적 사후 보관 기능입니다.

## 반드시 제공할 것 <span id="required-inputs-legacy"></span>

| 입력                | 요구사항                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| 대상 저장소         | 새 구현과 PR이 만들어질 Git 저장소 절대 경로                                                            |
| `mode`              | `legacy`                                                                                                |
| `legacyProjectRoot` | 대상과 다른 레거시 프로젝트의 절대 경로                                                                 |
| 이관 요청           | 루트 전체라면 “지정한 범위 전체를 이관해줘” 한 줄이면 충분. 일부만 옮길 때만 루트 안의 경로·화면을 추가 |
| `changeKind`        | `migration`                                                                                             |
| `scope`             | `ui`                                                                                                    |
| `publication`       | PR이면 `draft`, 발행하지 않으면 `none`                                                                  |

## 선택 입력 <span id="optional-inputs-legacy"></span>

- 두 프로젝트의 실행 명령, 테스트 계정, 경로와 화면 상태를 알려 주면 같은 조건의 기준 화면을 더 빠르게 준비할 수 있습니다.
- `legacyNetworkEvidencePath`: 코드만으로 HTTP 메서드와 경로를 확정할 수 없을 때 사용합니다. 해당 흐름만 캡처한 HAR/JSON을 대상 프로젝트 안의 `.gitignore` 적용 폴더에 저장하세요. 표준 HAR, `{requests:[{method,url}]}`, `[{method,url}]` 형식을 지원하며 최대 크기는 1MB, 요청 수는 1,000개입니다. 원본 헤더·쿠키·본문·쿼리는 장기 보관 자료나 PR에 복사하지 않습니다. 파일 위치, 해시, 정규화한 메서드·경로, 사용한 탐지 방식만 남깁니다.
- `briefPath`, `docsPaths`, `openApiPaths`, `openApiUrls`: 이관 범위를 보충하는 계약 근거입니다.
- `guidancePaths`, `skillHints`: 프로젝트 규칙과 적용할 수 있는 보조 스킬을 지정합니다.

## 기능 범위와 의존성 경계 <span id="scope-and-dependencies-legacy"></span>

`legacyProjectRoot`는 **변경할 수 없는 기능 범위**입니다. 다만 기능을 이해하는 데 필요한 의존성까지 모두 이 폴더 안에 있어야 한다는 뜻은 아닙니다. 경로·화면·상태·사용자 동작은 이 루트에서 만든 목록에서만 선택합니다. 루트 안의 코드가 가져오거나 설정에서 직접 참조하는 HTTP 클라이언트, 경로 별칭, 환경변수, 패키지·타입 선언, 상위 실행·빌드 설정은 기능을 이해하고 실행하는 데 필요한 만큼 확인할 수 있습니다. 이 자료는 선택한 기능을 해석하기 위한 근거일 뿐, 같은 저장소의 다른 기능까지 범위에 넣는 근거가 되지 않습니다. 저장소 전체 키워드 검색으로 범위를 넓히지도 않습니다.

`.env*`에서는 코드가 참조한 URL 계열 변수만 확인합니다. 사용자 정보·쿼리·해시를 제거한 안전한 원본 URL과 환경변수 이름을 `originRef`에 기록하며, 토큰·비밀번호 같은 비밀값은 결과물에 남기지 않습니다. 인증용 클라이언트와 기본 클라이언트의 차이도 호출 위치와 함께 기록해 대상 프로젝트 규칙에 맞춥니다.

## 최소 프롬프트 <span id="minimal-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy
scope: ui
legacyProjectRoot: /absolute/path/to/legacy-app
changeKind: migration
publication: draft
지정한 레거시 범위 전체를 대상 프로젝트 구조에 맞게 이관해줘.
레거시와 결과를 같은 경로·상태·화면 크기로 실행해 화면 일치율까지 비교하고 초안 PR로 발행해줘.
```

## 전체 프롬프트 예시 <span id="full-prompt-legacy"></span>

```text
/spec-to-pr /absolute/path/to/new-app
mode: legacy
scope: ui
legacyProjectRoot: /absolute/path/to/legacy-app

openApiPaths: [docs/legacy-api.yaml]
guidancePaths: [AGENTS.md, docs/architecture/ARCHITECTURE.md]
skillHints: [api-generator]
changeKind: migration
publication: draft
지정한 레거시 범위의 경로, 컴포넌트, API, 상태, 저장 방식을 목록으로 확정하고 대상 프로젝트로 이관해줘.
두 앱을 실행해 레거시 화면을 기준으로 삼고 같은 테스트 데이터·화면 크기의 결과와 비교해.
이전 코드를 그대로 복사하지 말고 대상 프로젝트의 구조와 지침에 맞게 개선하되 사용자 동작은 보존해.
```

## SpecToPR이 진행하는 과정 <span id="process-legacy"></span>

1. **접수 및 레거시 목록 작성:** 별도 루트를 읽기 전용으로 확인하고 경로, 컴포넌트, API, 상태, 저장 방식, 연결 코드, 자산을 범위가 제한된 `legacyInventory`로 정리합니다. 구문 트리는 실제 HTTP 요청만 `apiCandidates`로 수집하며 생성자와 로컬 파사드를 별도 API 작업으로 중복 등록하지 않습니다. HAR/JSON을 제공하면 원본 해시, `runtime-network-har` 탐지 방식, 확인된 메서드와 경로를 같은 목록의 해시에 묶습니다. 정적 분석과 제공된 OpenAPI만으로 메서드와 경로를 하나로 확정할 수 없으면 `collect-legacy-network-evidence`를 요청하고, `legacy-network-evidence`를 제출받아 같은 실행을 이어갑니다.
2. **계약 확정:** 안정적인 기능 키를 수용 조건과 `planned` 상태에 연결하고, 실행한 레거시 화면을 `visualTargets`로 확정합니다. 구현 전에는 이관 파일이나 검증 결과가 이미 있다고 주장하지 않습니다.
3. **구현:** 한 명의 구현 담당자가 대상 프로젝트의 규칙에 맞게 기능을 옮기고, 각 기능 키의 상태를 현재 검토 묶음의 `migrated` 또는 제외 상태로 바꿉니다. `legacyInventory`는 API 후보와 신뢰도를 기록합니다. 메서드·경로·body·인증·binding이 모호하면 추측해 쓰지 않고 **API Gap**으로 남기며, 확인된 화면·상태·라우트와 안전한 읽기 작업은 계속 구현합니다. HAR/JSON·OpenAPI는 같은 Run에서 Gap을 해소하는 선택 근거입니다.
4. **화면 비교 및 성능 측정:** 두 앱을 같은 경로·상태·테스트 데이터·화면 크기로 실행합니다. 각 캡처에는 기준과 같은 경로·상태·화면 크기·기기 배율·테스트 데이터, 자료 제공자, ISO 형식의 촬영 시각, PNG 경로, `sha256:` 해시를 기록합니다. `compare-visuals`는 비교 조건이 달라졌거나 해시가 일치하지 않으면 시도 횟수를 소비하지 않고 거부하며 정확 일치율·검토 일치율·차이 이미지·겹침 이미지를 계산합니다. 화면 일치율의 고정 기준은 92%, 근거가 있는 마스킹 영역은 최대 20%입니다. 최초 비교와 보정 후 최대 2회를 자동 수행하고, 세 번째 유효 실패는 실패 자료를 **화면 비교 Gap**으로 보존합니다. 집중 UI 검증은 전체 점수와 독립적입니다. Web Vitals도 함께 측정합니다.
5. **독립 검토:** 기능 검토자와 디자인 검토자가 이관 범위, 화면, 상호작용, 접근성을 각각 독립적으로 판정합니다.
6. **보고서 및 발행:** 리뷰어용 Legacy migration 본문에 원본→대상, 이관 범위, 레거시 화면 비교, API Gap을 정리하고 초안 PR을 만듭니다. Gap의 영향과 리뷰어 결정은 본문 최상단에 표시합니다.

각 보고서 섹션의 상태는 `complete`, `not-run`, `blocked`, `not-applicable` 중 하나입니다. 현재 검토 묶음에 속하지 않는 이전 경로는 PR에서 제외합니다. 초안 PR에는 레거시·이관 결과·차이 이미지와 일치율을 제공합니다. GitHub용 이미지는 실행마다 새 브랜치를 만들지 않고 관리 브랜치 `spec-to-pr/evidence`의 변경되지 않는 경로에 올린 뒤 업로드 커밋 SHA로 고정합니다.

## 단계와 작업 담당

| 단계                | 이 방식에서 수행하는 작업                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| `intake`            | 현재·목표 동작, 변경할 진입점, 범위, 발행 방식, 예상 작업량을 기록합니다.                                 |
| `contracts`         | `legacyInventory`, 예정된 이관 범위, 실행한 레거시 `visualTargets`, `requiredValidations`를 확정합니다.   |
| `implementation`    | 한 명의 구현 담당자가 기능을 옮기고, 안전하지 않은 쓰기로 이어질 수 없는 API 불확실성은 Gap으로 남깁니다. |
| `functional-review` | 읽기 전용 `functional-reviewer`가 변경 전후 자료와 관련 회귀 가능성을 판정합니다.                         |
| `design-review`     | UI가 바뀐 경우에만 읽기 전용 `design-reviewer`가 검토하며, 비-UI 작업에는 적용하지 않습니다.              |
| `report`            | 원본→대상, 이관 범위, 화면 비교, API Gap을 리뷰어 우선 본문으로 만듭니다.                                 |
| `publish`           | `publication: draft`이면 Gap·실패·미실행 증빙이 있어도 초안 PR/MR을 생성하거나 갱신할 수 있습니다.        |
| `archive`           | 병합이 확인된 뒤 사용자가 별도로 요청한 경우에만 실행합니다.                                              |

작업량이 XS/S이면 별도 조사 담당자를 두지 않고, M이면 최대 1명, L/XL이면 최대 2명의 읽기 전용 조사 담당자를 둘 수 있습니다. 큰 레거시 조사도 서로 독립적이고 편집이 필요 없는 범위로만 나눕니다. 구현 파일은 한 명만 편집하며 중첩 위임과 동시 편집은 허용하지 않습니다. UI 범위의 검토자 동시 실행은 구현이 끝난 뒤 작업량과 관계없이 사용하며, 두 판정은 같은 packet inbox에 보관합니다.

- `stageSkillRoute`: 공개 작업은 `intake-contracts` → `implement` → `review-functional` 순서로 진행합니다. UI가 바뀌면 `review-design`, 초안 발행이면 `publish`가 이어집니다. 이 경로는 `deliveryProfile.recommendedSkills`와 별개입니다.
- `recommendedSkills`: `figmaUrl`이 있으면 `figma`와 `design-system`, `openApiPaths`나 `openApiUrls`가 있으면 `api-generator`를 후보로 둡니다. React/Next 패키지가 확인되면 `react-best-practices`, `next-best-practices`를 선택 후보로 추가합니다.
- 레거시 UI라는 이유만으로 `playwright`를 추천하지 않습니다. `mode: feature`이고 UI 연결이 있을 때만 후보에 추가합니다.
- `appliedSkills`: 추천 스킬과 `skillHints` 중 실제로 설치되어 있고 현재 작업에 맞는 선택 스킬만 기록합니다. 선택 스킬이 없다는 이유로 기준 화면 비교나 필수 회귀 검증을 생략하지 않습니다.
- **워크플로 도구:** 상태를 보존하는 실행에 필수입니다. **Figma 호스트 기능:** `figmaUrl`이 있을 때만 필요합니다. **Playwright Test/CLI:** 변경 범위의 브라우저 회귀 검증이 필요할 때 정확한 선택자와 구조화 검증을 사용합니다. 전체 프로젝트 E2E나 영상은 요구하지 않습니다.
- **Browser MCP:** 상호작용을 재현하고 살펴볼 때 선택적으로 사용합니다. **Chrome DevTools MCP:** 콘솔·네트워크·성능·메모리·실시간 DOM의 원인을 진단할 때만 사용하며, 요구사항 통과 여부를 결정하지 않습니다.

### 정상 발행, 차단 진단, 재개

`workflow_publish`는 이관 범위와 코드 변경이 있으면 API Gap·화면 비교 실패·미실행 검토가 있어도 Draft PR을 만들 수 있습니다. 단, 이러한 Draft는 verified나 merge-ready가 아니며, `skipped`·`waived`도 통과로 표시하지 않습니다. 지원 원격 저장소·브랜치·커밋 차이 같은 발행 사전 조건을 충족하지 못하거나 `PUBLISH_NO_DELTA`이면 빈 커밋이나 이슈를 만들지 않고 **로컬 보고서**만 반환합니다.

`diagnostic-publication-uncertain`이 반환되면 자동으로 다시 발행하지 않습니다. GitHub/GitLab에서 소스·대상 브랜치가 같은 초안이 이미 만들어졌는지 확인해 사용자에게 보여 주고, 명시적인 승인을 받은 뒤에만 같은 `workflow_publish`를 `recoverUncertain: true`로 호출합니다.

입력이나 환경을 고친 뒤에는 새 실행을 만들지 않고 **같은 실행**의 최신 상태에서 이어갑니다. 진단용 초안이 있었다면 소스·대상 브랜치가 같은 **기존 초안 PR**의 `[Blocked]` 제목과 본문을 정상 `intent: ready` 내용으로 바꾸고 차단 라벨을 제거합니다.

## 검증 자료와 통과 기준 <span id="evidence-legacy"></span>

| 검증 자료  | 경로 예시                         | 통과 기준                                                     |
| ---------- | --------------------------------- | ------------------------------------------------------------- |
| 기능 목록  | `contracts/legacy-inventory.json` | 안정적인 기능 키와 소스 경로가 기록됨                         |
| 이관 범위  | `contracts/legacy-coverage.json`  | 모든 범위 키에 이관·제외·차이·차단 상태가 기록됨              |
| 화면 비교  | `visual/migration-report.json`    | 레거시/결과 일치율 ≥ 92%, 마스크 ≤ 20%, 차이·겹침 이미지 포함 |
| API 차이   | `evidence/api-coverage.json`      | 모든 API 후보의 구현·모의 응답·테스트 연결 또는 빈 목록 해시  |
| Web Vitals | `evidence/performance.json`       | 실험실 지표와 현장 자료 또는 미수집 사유                      |

경로는 `.spec-to-pr/<feature>/`를 기준으로 한 **예시**입니다. Figma 또는 UI 자료가 있으면 디자인 검증 자료가 추가되지만, 기능 개발용 영상까지 자동으로 요구하지는 않습니다.

### 초안 검토 자료의 위치

`publication: draft`인 레거시 이관의 검토 자료는 프로젝트 루트의 `.spec-to-pr/<feature>/`에 기능별로 모입니다. `<feature>`는 대개 레거시 루트 폴더 이름을 읽기 쉬운 슬러그로 바꿔 사용하며, 이름을 만들 수 없으면 안정적인 짧은 해시를 붙입니다. 어느 경우든 검토자가 내부 기능 키를 해석할 필요는 없습니다. `publication: none`이면 이 초안 전용 묶음을 요구하지 않습니다.

```text
.spec-to-pr/<feature>/
├── manifest.json        # 현재 실행·리비전과 입력 자료·요구사항·OpenSpec 해시
├── contracts/           # 수용 조건과 이관 범위
├── evidence/            # API·검증·성능 근거
├── visual/              # 레거시 / 현재 PNG와 비교 결과
└── report/              # 초안 PR에 쓰이는 검토자용 JSON/Markdown

openspec/changes/<change-name>/
├── proposal.md
├── specs/<capability>/spec.md
└── tasks.md
```

`manifest.json`은 현재 Run·리비전, 레거시 루트 해시, 요구사항 ID와 선택적으로 연결한 OpenSpec 파일 해시를 묶습니다. OpenSpec이 없는 core Run도 유효하며, OpenSpec을 연결한 경우에만 그 파일의 변경을 검증합니다. PR 본문에는 요구사항 제목·상태·결과 파일과 **레거시/현재 화면 나란히 보기**를 먼저 보여 줍니다. 차이 이미지는 별도 검토 자료로 연결하고 일치율을 함께 표시합니다. 내부 기능 키와 반복되는 전체 구현 파일 목록은 기본적으로 숨깁니다. 원본 HAR, 쿠키, 토큰, 전체 로그도 이 폴더나 PR에 복사하지 않습니다.

### GitLab 이미지 업로드가 실패할 때

GitLab 프로젝트 이미지 업로드가 인증 오류, 일시적인 네트워크 오류, 5xx 응답으로 실패하면 검증을 마친 레거시/현재 PNG만 검토 대상 커밋의 원본(raw) URL로 대신 연결해 초안 PR 발행을 이어갈 수 있습니다. 먼저 파일이 Git에서 추적하는 일반 파일인지 확인합니다. 검토 대상 커밋의 정확한 파일과 깨끗한 작업 트리 파일이 모두 캡처할 때 기록한 해시와 같아야 합니다. 생성된 차이·겹침 이미지, 영상, 누락되거나 변경된 파일, 해시가 다른 파일에는 이 방식을 사용하지 않고 정확한 실패 원인을 남깁니다.

## 예상 브랜치와 커밋 <span id="branch-and-commits-legacy"></span>

- 브랜치 예시: `codex/legacy-scope-migration`
- 커밋 예시: `feat: migrate selected legacy scope`
- 대규모 서식 변경, 의존성 업그레이드, 관련 없는 정리는 같은 커밋에 섞지 않습니다.
- 발행하기 전에 작업 트리가 깨끗하고 소스 브랜치가 대상 브랜치보다 앞서 있는지 확인합니다.

## 예상 초안 PR <span id="expected-pr-legacy"></span>

**제목 예시:** `feat: migrate selected legacy scope`

```md
## 레거시 이관

- 매장 탐색 및 상세: 이관 완료 → src/pages/shop

## 화면 일치율

- 실행한 레거시와 현재 화면: 98.62%
- 레거시 / 현재 / 차이 이미지와 일치율

## API·성능·검토

- 확인한 API: 4/4 검증, 미해결 없음
- LCP 2.2s, CLS 0.03, TBT 140ms
- 기능 검토: 승인
- 디자인·접근성 검토: 승인

## 위험과 되돌리기

- 지정한 레거시 범위 외 동작은 변경하지 않음
- 되돌릴 수 있는 단일 커밋
```

## 실행이 멈추는 경우 <span id="blockers-legacy"></span>

| 중단 원인                                      | 사용자가 할 일                                   |
| ---------------------------------------------- | ------------------------------------------------ |
| `legacyProjectRoot`가 없거나 대상과 같음       | 별도 레거시 디렉터리 절대 경로 제공              |
| `LEGACY_API_METHOD_UNKNOWN`                    | 안내에서 요청한 범위 제한 HAR을 같은 실행에 제출 |
| HAR/JSON이 1MB·요청 1,000개 한도나 형식을 위반 | 해당 흐름만 다시 캡처해 제한 형식으로 저장       |
| 레거시/대상 앱을 실행할 수 없음                | 실행 명령, 테스트 데이터, 환경 조건 제공         |
| 기준 화면과 소스 자료가 충돌                   | 기대 동작의 기준 자료를 선택                     |
| 검사 환경이 없어 필수 회귀 검증을 만들 수 없음 | 최소 실행 방법이나 승인된 대체 증거 제공         |
| 발행 사전 검사 실패                            | 변경을 정리·커밋해 깨끗한 소스 브랜치로 재개     |

## 이 케이스가 하지 않는 것 <span id="exclusions-legacy"></span>

- 의존성 폴더나 빌드 결과물을 무제한으로 훑거나 레거시 저장소를 편집하지 않습니다.
- 이전 코드를 무조건 복사하거나 현재 대상 프로젝트의 구조를 훼손하지 않습니다.
- 전체 프로젝트 E2E나 기능 영상을 자동으로 요구하지 않습니다.
- Figma를 화면 기준으로 사용하지 않습니다. 이 방식의 기준은 실제로 실행한 레거시입니다.
