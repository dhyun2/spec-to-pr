Intake 직후 `XS`~`XL` workload, 예상 token range, confidence와 근거가 표시됩니다. 이는 고정 약속이 아닙니다. 80% 경계에서는 checkpoint와 compact context로 이어가며, 한계에 도달해도 `requiredValidations`를 빼지 않고 범위를 나누거나 사용자의 결정을 기다립니다.

## 이 케이스를 쓰는 경우 <span id="use-this-case-figma"></span>

Figma가 primary source이고 실제 API 없이 mock 데이터로 화면을 구현할 때 사용합니다. 연결된 호스트에서 node와 PNG baseline을 읽어 기존 디자인 시스템에 매핑하고, 결과 화면과 수치 비교한 뒤 **기본 draft PR**을 만듭니다.

:::tip[입력 / 결과]
**입력:** 저장소 + 유효한 Figma URL · **결과:** mock-backed UI, Figma 일치율/diff/overlay, 독립 리뷰, 15개 섹션 draft PR
:::

## 반드시 제공할 것 <span id="required-inputs-figma"></span>

| 입력          | 요구사항                                         |
| ------------- | ------------------------------------------------ |
| 저장소        | 디자인 시스템과 화면을 구현할 대상 Git 저장소    |
| `mode`        | `figma`                                          |
| `scope`       | `ui` 필수                                        |
| `figmaUrl`    | 접근 가능한 file URL과 가능하면 구체적 `node-id` |
| `publication` | 기본값은 `draft`; 구현·리뷰까지만이면 `none`     |
| 요청          | 구현할 화면·상태·반응형 범위를 지정              |

## 선택 입력 <span id="optional-inputs-figma"></span>

- `briefPath`, `docsPaths`: 화면의 문구와 상태 설명을 보충합니다.
- `guidancePaths`: design-system 사용법, architecture, folder-structure를 명시합니다.
- `skillHints`: 설치된 `design-system`, React/Next 성능, accessibility 관련 skill을 적용하도록 요청합니다.

## 최소 프롬프트 <span id="minimal-prompt-figma"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: figma
scope: ui
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
publication: draft
Figma를 deterministic mock 데이터로 구현하고 결과 화면과 98% 기준으로 비교한 뒤 draft PR로 발행해줘.
```

## 전체 프롬프트 예시 <span id="full-prompt-figma"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: figma
scope: ui
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
docsPaths: [docs/checkout-states.md]
guidancePaths: [docs/design-system.md, docs/etc/folder-structure.md]
skillHints: [design-system, react-best-practices, accessibility-auditor]
changeKind: design
publication: draft
node 12:345의 desktop/mobile과 loading/error/success 상태를 기존 컴포넌트로 구현해줘.
실제 Figma bundle과 `visualTargets`를 만들고 mock으로 모든 상태를 고정해.
결과 화면의 exact/review ratio, diff, overlay와 독립 리뷰를 만든 뒤 draft PR로 발행해줘.
```

## SpecToPR이 진행하는 과정 <span id="process-figma"></span>

1. **Intake:** URL, node, 화면/상태 범위, publication intent와 workload 추정을 확인합니다.
2. **Figma contracts:** 연결된 호스트에서 node IDs, variables, component context, screenshots, assets를 읽고 project-local strict manifest를 만듭니다.
3. **Design-system mapping:** 새 custom markup 전에 기존 component/token과 상태를 대응시킵니다.
4. **Implementation:** `{deterministic:true, fixtures:[{path, sha256}]}` 형태의 strict mock JSON manifest와 별도 fixture를 제출합니다. 각 `sha256:` digest로 fixture 내용을 고정하고 반응형 layout, interaction, loading/error/empty/success 상태를 구현합니다.
5. **Compare / reviews:** 각 actual capture는 target의 route/state/viewport/device scale/fixture를 반복하고 provider, ISO capture time, PNG path, `sha256:` digest를 기록합니다. `compare-visuals`는 target drift·digest mismatch를 거부한 뒤 같은 viewport의 exact/review ratio, masks, diff, overlay를 계산합니다. 런타임 최소 98%, 정당한 mask 최대 20%, 비교 총 3회(최초 1회 + repair 최대 2회)이며 reviewer가 접근성과 interaction을 별도 판정합니다.
6. **Report / publish:** `pr-report-v2.1` 15개 섹션을 만들고 draft PR을 발행합니다.

각 보고서 섹션은 `complete`, `not-run`, `blocked`, `not-applicable` 중 하나입니다. 현재 review packet에 속하지 않는 stale path는 PR에서 생략합니다. GitHub 이미지·diff·overlay는 실행별 branch가 아니라 단일 관리 branch `spec-to-pr/evidence`의 immutable 경로에 올리고 upload commit SHA로 고정합니다.

## 실행 정책: stage, agent, skill, tool

| Durable stage       | 이 케이스의 정확한 동작                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| `intake`            | Figma file/node, UI 상태·반응형 범위, publication과 workload를 고정합니다.                               |
| `contracts`         | connected host에서 실제 node/variables/assets/screenshot을 읽고 strict `figma-bundle`을 제출합니다.      |
| `implementation`    | 한 명의 implementation writer가 기존 design system에 매핑하고 deterministic mock-backed UI를 구현합니다. |
| `functional-review` | read-only `functional-reviewer`가 상태 동작과 관련 project check를 판정합니다.                           |
| `design-review`     | read-only `design-reviewer`가 Figma 대비 visual/interaction/responsive/accessibility를 판정합니다.       |
| `report`            | `pr-report-v2.1` 15개 섹션에 provenance, visual ratio/assets, review, gap, blocker를 기록합니다.         |
| `publish`           | ready이면 packet-bound body와 visual assets를 포함한 draft를 만듭니다.                                   |
| `archive`           | 발행한 draft가 merge된 뒤 authoritative evidence와 별도 요청으로만 실행합니다.                           |

Agent 정책은 XS/S read-only scout 0명, M 최대 1명, L/XL 최대 2명입니다. Scout는 큰 Figma/repository mapping의 독립적인 read-heavy discovery만 수행합니다. 한 implementation writer만 편집하며 **no nesting**, **parallel writer 금지**입니다. 두 reviewer는 L/XL의 implementation 뒤에만 병렬일 수 있습니다.

- `stageSkillRoute`: public action은 `intake-contracts` → `implement` → `review-functional`/`review-design` 순서이며 draft면 `publish`로 이어집니다. 이 routing은 `deliveryProfile.recommendedSkills`가 아닙니다.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; 감지된 React/Next package → `react-best-practices`, `next-best-practices` optional candidate입니다.
- Figma UI라는 이유만으로 `playwright`를 추천하지 않습니다. `mode: feature` + UI mapping만 해당 candidate를 추가합니다.
- `appliedSkills`: `recommendedSkills`와 available/applicable한 `skillHints`의 optional-skill 허용 합집합만 기록합니다. Missing optional skill은 blocker가 아니지만 real Figma evidence는 선택이 아닙니다.
- **workflow MCP:** 필수. **Figma host:** URL의 file/node를 읽는 데 필수이며 runtime polling으로 대체할 수 없습니다. **Playwright Test/CLI:** runtime UI assertion이 `requiredValidations`에 있으면 focused check로 사용하지만 feature E2E나 video는 요구하지 않습니다.
- **Browser MCP:** optional interactive visual inspection. **Chrome DevTools MCP:** console/network/performance/memory/live-DOM 진단에만 conditional입니다. Screenshot/DevTools 관찰은 Playwright assertion을 대신하지 않습니다.

### Ready, blocked diagnostic, resume

정상 결과는 `workflow_publish intent: ready`의 evidence-backed draft입니다. 정상/blocked 모두 같은 `pr-report-v2.1` 15개 섹션을 사용합니다. Figma/browser evidence가 없으면 `BROWSER_NOT_RUN` 같은 typed `blockerDetails`, 미실행 검증, exact unblock action을 남깁니다. Preflight가 허용할 때만 `workflow_publish intent: blocked-diagnostic` draft를 만들며 계속 `status: blocked`입니다. 조건이 없거나 `PUBLISH_NO_DELTA`면 empty commit/issue fallback 없이 **local blocked report**를 반환합니다.

명시적으로 draft를 요청한 실행이 `diagnostic-publication-uncertain`이면 자동 재발행하지 않습니다. GitHub/GitLab에서 matching draft를 확인해 사용자에게 보여주고, 명시적 승인을 받은 경우에만 같은 `workflow_publish`를 `recoverUncertain: true`로 호출합니다.

권한·node·evidence를 고친 뒤 **same Run**의 latest status에서 재개합니다. Diagnostic draft가 있었다면 같은 source/target의 **same draft PR**을 `[Blocked]`에서 정상 `intent: ready` 제목/본문으로 갱신하고 blocked label을 제거합니다.

## 증거와 검증 <span id="evidence-figma"></span>

| 증거                   | 예상 예시                                                            | 통과 기준                                                                                   |
| ---------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| bundle                 | `evidence/figma/figma-bundle.json`                                   | `provider: host-connected-figma`, ISO `capturedAt`, matching `fileUrl`, non-empty `nodeIds` |
| manifest/visuals       | `evidence/figma/manifest.json`, `evidence/figma/checkout-mobile.png` | project-local strict manifest와 실제 PNG `visualPaths`                                      |
| visual comparison      | `evidence/visual/figma-report.json`                                  | exact/review ratio ≥ 98%, baseline/target/diff/overlay                                      |
| mock fixtures          | `evidence/fixtures/checkout.json`                                    | deterministic loading/error/empty/success 데이터                                            |
| responsive/interaction | `evidence/design/responsive.json`, `interaction.json`                | 지정 viewport와 상태 전이가 검증됨                                                          |
| accessibility          | `evidence/design/accessibility.json`                                 | semantic/keyboard/focus/contrast 검사가 성공                                                |
| design review          | `evidence/reviews/design.json`                                       | 고정된 diff와 evidence에 대한 독립 approved verdict                                         |

Figma mode는 기능 개발용 targeted E2E와 영상을 자동으로 요구하지 않습니다. 기능 전체와 영상 납품이 목적이면 `mode: feature`를 선택하고 `figmaUrl`을 source로 조합합니다.

## 예상 브랜치와 커밋 <span id="branch-and-commits-figma"></span>

- 예상 브랜치: `codex/figma-checkout`
- 커밋 예상 예시: `feat: implement checkout from Figma`
- draft 발행 전에는 다른 케이스와 동일하게 committed source branch와 clean tree가 필수입니다.

## 예상 Draft PR <span id="expected-pr-figma"></span>

**예상 예시 제목:** `feat: implement checkout from Figma`

```md
## Figma source

- file/node: checkout / 12:345
- bundle: evidence/figma/figma-bundle.json

## Implementation

- existing design-system components와 tokens 사용
- desktop/mobile, loading/error/success 상태 구현

## Design validation

- exact match: 97.84%; review match: 99.12%; threshold: 98%
- baseline / target / diff / overlay links
- responsive / interaction / accessibility: passed
- design-reviewer: approved

## Known differences

- Figma에 정의되지 않은 상태와 의도적으로 제외한 범위
```

## Run이 멈추는 경우 <span id="blockers-figma"></span>

| 중단 원인                                 | 사용자가 할 일                                        |
| ----------------------------------------- | ----------------------------------------------------- |
| URL/node가 잘못되었거나 권한 없음         | 접근 가능한 URL과 정확한 node-id 제공                 |
| connected-host evidence를 읽을 수 없음    | Figma 연결·로그인·권한을 복구하고 재개                |
| required state/viewport가 Figma에 없음    | authoritative behavior 또는 승인된 보완 요구사항 제공 |
| 기존 design-system과 Figma가 충돌         | 재사용/확장/예외 중 원하는 방향을 결정                |
| draft 요청인데 branch가 dirty/uncommitted | 의도한 파일만 커밋해 clean preflight를 충족           |

## 이 케이스가 하지 않는 것 <span id="exclusions-figma"></span>

- URL만으로 node, variable, component를 봤다고 주장하지 않습니다.
- Figma를 polling하거나 별도 runtime microtool을 추가하지 않습니다.
- 실제 API client, API gap, Web Vitals, feature E2E와 영상을 기본 계약에 추가하지 않습니다.
- 기능 개발 모드의 full feature E2E와 영상 계약을 암묵적으로 추가하지 않습니다.
