요청을 접수하면 `XS`~`XL` 예상 작업량, 토큰 범위, 신뢰도와 산정 근거를 먼저 보여 줍니다. 이 값은 확정된 약속이 아닙니다. 사용량이 80%에 이르면 진행 상태를 저장하고 간결한 맥락으로 이어갑니다. 한계에 도달해도 `requiredValidations`를 줄이지 않고, 검증 가능한 단위로 범위를 나누거나 사용자의 결정을 기다립니다.

## 이 사용법을 쓰는 경우 <span id="use-this-case-figma"></span>

Figma를 기준으로 실제 API 없이 고정된 모의 데이터로 화면을 구현할 때 사용합니다. 연결된 호스트에서 노드와 기준 PNG를 읽어 기존 디자인 시스템에 연결하고, 결과 화면을 수치로 비교한 뒤 **초안 PR**을 만듭니다.

:::tip[입력 / 결과]
**입력:** 저장소 + 유효한 Figma URL · **결과:** 모의 데이터 기반 UI, Figma 일치율과 차이·겹침 이미지, 독립 검토, 15개 섹션 초안 PR
:::

## 반드시 제공할 것 <span id="required-inputs-figma"></span>

| 입력          | 요구사항                                         |
| ------------- | ------------------------------------------------ |
| 저장소        | 디자인 시스템과 화면을 구현할 대상 Git 저장소    |
| `mode`        | `figma`                                          |
| `scope`       | `ui` 필수                                        |
| `figmaUrl`    | 접근 가능한 파일 URL과 가능하면 구체적 `node-id` |
| `publication` | 기본값은 `draft`; 구현·검토까지만이면 `none`     |
| 요청          | 구현할 화면·상태·반응형 범위를 지정              |

## 선택 입력 <span id="optional-inputs-figma"></span>

- `briefPath`, `docsPaths`: 화면의 문구와 상태 설명을 보충합니다.
- `guidancePaths`: 디자인 시스템 사용법, 구조 문서, 폴더 구성 문서를 명시합니다.
- `skillHints`: 설치된 `design-system`, React/Next 성능, 접근성 관련 스킬을 요청합니다.

## 최소 프롬프트 <span id="minimal-prompt-figma"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: figma
scope: ui
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
publication: draft
Figma를 고정된 모의 데이터로 구현하고 결과 화면과 98% 기준으로 비교한 뒤 초안 PR로 발행해줘.
```

## 전체 프롬프트 예시 <span id="full-prompt-figma"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: figma
scope: ui
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
docsPaths: [docs/checkout-states.md]
guidancePaths: [docs/design-system.md, docs/etc/folder-structure.md]
skillHints: [design-system, react-best-practices, accessibility-auditor]
changeKind: design
publication: draft
노드 12:345의 데스크톱·모바일 화면과 로딩·오류·성공 상태를 기존 컴포넌트로 구현해줘.
실제 Figma 자료 묶음과 `visualTargets`를 만들고 모의 데이터로 모든 상태를 고정해.
결과 화면의 정확 일치율·검토 일치율, 차이·겹침 이미지와 독립 검토를 만든 뒤 초안 PR로 발행해줘.
```

## SpecToPR이 진행하는 과정 <span id="process-figma"></span>

1. **접수:** URL, 노드, 화면·상태 범위, 발행 의도, 예상 작업량을 확인합니다.
2. **Figma 계약 확정:** 연결된 호스트에서 노드 ID, 변수, 컴포넌트 맥락, 화면, 자산을 읽고 프로젝트 안에 엄격한 매니페스트를 만듭니다.
3. **디자인 시스템 연결:** 새 마크업을 만들기 전에 기존 컴포넌트·토큰과 각 상태를 대응시킵니다.
4. **구현:** `{deterministic:true, fixtures:[{path, sha256}]}` 형태의 엄격한 모의 데이터 JSON 매니페스트와 별도 테스트 데이터를 제출합니다. 각 `sha256:` 해시로 내용을 고정하고 반응형 레이아웃, 상호작용, 로딩·오류·빈 화면·성공 상태를 구현합니다.
5. **화면 비교 및 검토:** 각 결과 화면에는 기준과 같은 경로·상태·화면 크기·기기 배율·테스트 데이터, 자료 제공자, ISO 형식의 촬영 시각, PNG 경로, `sha256:` 해시를 기록합니다. `compare-visuals`는 비교 조건이나 해시가 달라지면 거부한 뒤 정확 일치율·검토 일치율·마스킹 영역·차이 이미지·겹침 이미지를 계산합니다. 기준은 일치율 98% 이상, 근거가 있는 마스킹 영역 20% 이하이며, 최초 비교 1회와 보정 후 최대 2회를 합쳐 모두 3번까지 비교할 수 있습니다. 검토자는 접근성과 상호작용을 별도로 판정합니다.
6. **보고서 및 발행:** `pr-report-v2.1` 15개 섹션을 만들고 초안 PR을 발행합니다.

각 보고서 섹션은 `complete`, `not-run`, `blocked`, `not-applicable` 중 하나입니다. 현재 검토 묶음에 속하지 않는 이전 검증 자료는 PR에서 제외합니다. 초안 PR에는 Figma 기준·결과·차이 이미지와 일치율을 제공합니다. GitHub용 이미지는 실행마다 새 브랜치를 만들지 않고 관리 브랜치 `spec-to-pr/evidence`의 변경되지 않는 경로에 올린 뒤 업로드 커밋 SHA로 고정합니다.

## 단계와 작업 담당

| 단계                | 이 방식에서 수행하는 작업                                                                    |
| ------------------- | -------------------------------------------------------------------------------------------- |
| `intake`            | Figma 파일·노드, UI 상태·반응형 범위, 발행 방식, 예상 작업량을 고정합니다.                   |
| `contracts`         | 연결된 호스트에서 실제 노드·변수·자산·화면을 읽고 엄격한 `figma-bundle`을 제출합니다.        |
| `implementation`    | 한 명의 구현 담당자가 기존 디자인 시스템에 연결하고 고정된 모의 데이터 기반 UI를 구현합니다. |
| `functional-review` | 읽기 전용 `functional-reviewer`가 상태 동작과 관련 프로젝트 검사를 판정합니다.               |
| `design-review`     | 읽기 전용 `design-reviewer`가 Figma 대비 화면·상호작용·반응형 상태·접근성을 판정합니다.      |
| `report`            | `pr-report-v2.1` 15개 섹션에 출처, 화면 일치율·자료, 검토, 차이, 차단 사유를 기록합니다.     |
| `publish`           | 검증을 통과하면 검토 묶음에 연결된 본문과 화면 자료가 있는 초안을 만듭니다.                  |
| `archive`           | 발행한 초안이 병합되었다는 근거가 있고 사용자가 별도로 요청한 경우에만 실행합니다.           |

작업량이 XS/S이면 별도 조사 담당자를 두지 않고, M이면 최대 1명, L/XL이면 최대 2명의 읽기 전용 조사 담당자를 둘 수 있습니다. 조사 담당자는 큰 Figma 자료와 저장소의 대응 관계처럼 서로 겹치지 않는 항목만 탐색합니다. 구현은 한 명의 담당자만 편집하며 중첩 위임과 여러 구현 담당자의 동시 편집은 허용하지 않습니다. 두 검토는 L/XL 구현이 끝난 뒤에만 동시에 진행할 수 있습니다.

<details>
<summary>스킬과 도구의 세부 규칙</summary>

- `stageSkillRoute`: 공개 작업은 `intake-contracts` → `implement` → `review-functional`/`review-design` 순서로 진행하며, 초안 발행이면 `publish`가 이어집니다. 이 경로는 `deliveryProfile.recommendedSkills`와 다릅니다.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; 감지된 React/Next 패키지 → `react-best-practices`, `next-best-practices`
- Figma UI라는 이유만으로 `playwright`를 추천하지 않습니다. `mode: feature`이고 UI 연결이 있을 때만 후보에 추가합니다.
- `appliedSkills`: `recommendedSkills`와 실제로 설치되어 있고 현재 작업에 맞는 `skillHints`만 기록합니다. 선택 스킬이 없어도 실행을 중단하지 않지만 실제 Figma 검증 자료는 반드시 필요합니다.
- **워크플로 도구:** 필수입니다. **Figma 호스트 기능:** URL의 파일과 노드를 읽는 데 필수이며 반복 상태 조회로 대신할 수 없습니다. **Playwright Test/CLI:** 실행 화면 검증이 `requiredValidations`에 있으면 관련 검사에 사용하지만 기능 E2E나 영상은 요구하지 않습니다.
- **Browser MCP:** 상호작용과 화면을 살펴볼 때 선택적으로 사용합니다. **Chrome DevTools MCP:** 콘솔·네트워크·성능·메모리·실시간 DOM 문제를 진단할 때만 사용합니다. 스크린샷이나 DevTools 관찰은 Playwright 검증을 대신하지 않습니다.

</details>

### 정상 발행, 차단 진단, 재개

정상 흐름에서는 `workflow_publish intent: ready`로 검증 자료가 포함된 초안을 만듭니다. 정상 발행과 차단 진단은 같은 `pr-report-v2.1` 15개 섹션을 사용합니다. Figma나 브라우저 검증 자료가 없으면 `BROWSER_NOT_RUN` 같은 구조화된 `blockerDetails`, 실행하지 못한 검증, 정확한 해결 방법을 남깁니다. 발행 사전 조건을 충족할 때만 `workflow_publish intent: blocked-diagnostic`으로 진단용 초안을 만들며 상태는 계속 `status: blocked`입니다. 조건을 충족하지 못하거나 `PUBLISH_NO_DELTA`가 발생하면 빈 커밋이나 대체 이슈를 만들지 않고 **로컬 차단 보고서**를 반환합니다.

명시적으로 초안을 요청한 실행이 `diagnostic-publication-uncertain`을 반환하면 자동으로 다시 발행하지 않습니다. GitHub/GitLab에서 소스와 대상 브랜치가 같은 기존 초안을 확인해 사용자에게 보여 주고, 명시적인 승인을 받은 경우에만 같은 `workflow_publish`를 `recoverUncertain: true`로 호출합니다.

권한·노드·검증 자료를 고친 뒤 최신 상태의 **같은 실행**을 재개합니다. 진단용 초안이 있었다면 소스와 대상 브랜치가 같은 **기존 초안 PR**의 `[Blocked]` 제목·본문을 정상 `intent: ready` 내용으로 바꾸고 차단 라벨을 제거합니다.

## 검증 자료와 통과 기준 <span id="evidence-figma"></span>

| 검증 자료       | 예상 예시                                                            | 통과 기준                                                                                        |
| --------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Figma 자료 묶음 | `evidence/figma/figma-bundle.json`                                   | `provider: host-connected-figma`, ISO `capturedAt`, 일치하는 `fileUrl`, 비어 있지 않은 `nodeIds` |
| 화면 목록       | `evidence/figma/manifest.json`, `evidence/figma/checkout-mobile.png` | 프로젝트 안의 엄격한 목록과 실제 PNG `visualPaths`                                               |
| 화면 비교       | `evidence/visual/figma-report.json`                                  | 검토 일치율 98% 이상, 기준·결과·차이·겹침 이미지                                                 |
| 모의 데이터     | `evidence/fixtures/checkout.json`                                    | 고정된 로딩·오류·빈 화면·성공 데이터                                                             |
| 반응형·상호작용 | `evidence/design/responsive.json`, `interaction.json`                | 지정한 화면 크기와 상태 전이를 검증함                                                            |
| 접근성          | `evidence/design/accessibility.json`                                 | 의미 구조·키보드·초점·명암비 검사가 성공                                                         |
| 디자인 검토     | `evidence/reviews/design.json`                                       | 고정된 차이 이미지와 검증 자료에 대한 독립 판정이 승인됨                                         |

Figma 방식은 기능 개발용 E2E와 영상을 자동으로 요구하지 않습니다. 기능 전체와 영상까지 필요하면 `mode: feature`를 선택하고 `figmaUrl`을 입력 자료로 함께 제공합니다.

## 예상 브랜치와 커밋 <span id="branch-and-commits-figma"></span>

- 예상 브랜치: `codex/figma-checkout`
- 커밋 예상 예시: `feat: implement checkout from Figma`
- 초안 발행 전에는 다른 사용법과 마찬가지로 커밋한 소스 브랜치와 깨끗한 작업 트리가 필요합니다.

## 예상 초안 PR <span id="expected-pr-figma"></span>

**예상 예시 제목:** `feat: implement checkout from Figma`

```md
## Figma 출처

- 파일/노드: checkout / 12:345
- 자료 묶음: evidence/figma/figma-bundle.json

## 구현

- 기존 디자인 시스템 컴포넌트와 토큰 사용
- 데스크톱/모바일, 로딩/오류/성공 상태 구현

## 디자인 검증

- 정확 일치율: 97.84%, 검토 일치율: 99.12%, 통과 기준: 98%
- 기준 / 결과 / 차이 이미지와 일치율
- 반응형 / 상호작용 / 접근성: 통과
- design-reviewer: approved

## 알려진 차이

- Figma에 정의되지 않은 상태와 의도적으로 제외한 범위
```

## 실행이 멈추는 경우 <span id="blockers-figma"></span>

| 중단 원인                                | 사용자가 할 일                                    |
| ---------------------------------------- | ------------------------------------------------- |
| URL·노드가 잘못되었거나 권한이 없음      | 접근 가능한 URL과 정확한 `node-id` 제공           |
| 연결된 호스트에서 자료를 읽을 수 없음    | Figma 연결·로그인·권한을 복구하고 재개            |
| 필요한 상태·화면 크기가 Figma에 없음     | 기준으로 삼을 동작 또는 승인된 보완 요구사항 제공 |
| 기존 디자인 시스템과 Figma가 충돌        | 재사용·확장·예외 중 원하는 방향을 결정            |
| 초안 요청인데 브랜치가 불결하거나 미커밋 | 의도한 파일만 커밋해 깨끗한 사전 상태를 충족      |

## 이 사용법이 하지 않는 것 <span id="exclusions-figma"></span>

- URL만으로 노드·변수·컴포넌트를 확인했다고 주장하지 않습니다.
- Figma 상태를 반복 조회하거나 별도 실행 도구를 추가하지 않습니다.
- 실제 API 클라이언트, API 누락 현황, Web Vitals, 기능 E2E와 영상을 기본 계약에 추가하지 않습니다.
- 기능 개발 방식의 전체 기능 E2E와 영상 계약을 암묵적으로 추가하지 않습니다.
