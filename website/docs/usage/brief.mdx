Intake 직후 `XS`~`XL` workload, 예상 token range, confidence와 근거가 표시됩니다. 이는 고정 약속이 아닙니다. 80% 경계에서는 checkpoint와 compact context로 이어가며, 한계에 도달해도 `requiredValidations`를 빼지 않고 범위를 나누거나 사용자의 결정을 기다립니다.

## 이 케이스를 쓰는 경우 <span id="use-this-case-brief"></span>

기획서·Figma·API 문서를 한 번에 주고 화면과 API를 끝까지 구현한 draft PR을 받고 싶을 때 사용합니다. 이 케이스는 “기획서만 읽는 가벼운 작업”이 아니라 전체 프로세스 개발입니다. 기능 전체 E2E와 영상은 제외하지만, Figma 대비 화면 일치율, API 사용/갭, Web Vitals는 필수입니다.

:::tip[입력 / 결과]
**입력:** 대상 저장소 + 기획서(PDF/MD 등) + Figma URL + OpenAPI 경로/URL · **결과:** API/UI 구현, 수치화된 화면 비교, API gap, Web Vitals, 15개 섹션 draft PR
:::

## 반드시 제공할 것 <span id="required-inputs-brief"></span>

| 입력          | 요구사항                                                         |
| ------------- | ---------------------------------------------------------------- |
| 저장소        | 절대 경로이며 Git 저장소여야 합니다. 예: `/absolute/path/to/app` |
| `mode`        | `brief`                                                          |
| `briefPath`   | PDF/MD 등 실제 기획서 파일. 예: `docs/checkout.pdf`              |
| `figmaUrl`    | 구현할 file/node URL. 실제 PNG baseline을 수집합니다.            |
| OpenAPI       | `openApiPaths` 또는 HTTPS `openApiUrls` 중 하나 이상             |
| 요청          | “구현해줘”만 쓰지 말고 어떤 수용 조건을 납품할지 적습니다.       |
| `changeKind`  | 실제 변경에 맞는 `feature`, `fix`, `refactor`, `docs` 등         |
| `publication` | PR까지 원하면 `draft`; 구현·리뷰까지만이면 `none`                |

## 선택 입력 <span id="optional-inputs-brief"></span>

- `scope: ui`: 이 케이스의 기본 UI 계약을 명시합니다.
- `docsPaths`: 비즈니스 규칙, 오류 사례, 분석 문서 등 보조 source입니다.
- `guidancePaths`: `AGENTS.md`, architecture, folder-structure 같은 프로젝트 지침을 명시합니다.
- `skillHints`: 설치되어 있고 적용 가능한 skill만 사용하도록 힌트를 줍니다. 누락된 선택 skill은 blocker가 아닙니다.

## 최소 프롬프트 <span id="minimal-prompt-brief"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: brief
briefPath: docs/checkout.md
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
openApiPaths: [docs/openapi.yaml]
changeKind: feature
publication: draft
기획서의 수용 조건만 구현하고 관련 검사로 검증한 뒤 draft PR로 발행해줘.
```

## 전체 프롬프트 예시 <span id="full-prompt-brief"></span>

```text
/spec-to-pr /absolute/path/to/app
mode: brief
scope: ui
briefPath: docs/checkout.md
figmaUrl: https://www.figma.com/design/FILE/checkout?node-id=12-345
openApiPaths: [docs/openapi.yaml]
docsPaths: [docs/business-rules.md, docs/error-cases.md]
guidancePaths: [docs/architecture/ARCHITECTURE.md, docs/etc/folder-structure.md]
skillHints: [react-best-practices, next-best-practices, design-system, api-generator]
changeKind: feature
publication: draft
기획서의 승인된 checkout 수용 조건만 구현해줘. 문서 사이에 충돌이 있으면 추측하지 말고 멈춰.
API 계약 증거를 먼저 만든 뒤 같은 implementation context에서 UI를 구현하고 관련 검사만 실행해.
```

## SpecToPR이 진행하는 과정 <span id="process-brief"></span>

1. **Intake:** 경로와 publication intent를 정규화하고 workload/token range/confidence를 표시합니다.
2. **Contracts:** raw digest가 있는 `sourceProvenance`, 수용 조건, API operation, Figma `visualTargets`를 고정합니다.
3. **Implementation:** 같은 `implementationContextId`에서 API types/schema/wrapper/mock/contract test를 먼저 만들고 UI를 연결합니다. 최종 `apiCoverage`가 production call, mock, executable proof를 operation별로 매핑합니다.
4. **Visual / performance:** 같은 route/state/fixture/viewport에서 Figma PNG와 결과 화면을 `compare-visuals`로 비교합니다. 각 actual capture는 target의 route/state/viewport/device scale/fixture를 반복하고 provider, ISO capture time, PNG path, `sha256:` digest를 기록합니다. 런타임이 target drift·digest mismatch를 거부하고 exact/review ratio, diff, overlay를 최소 98%, 정당한 mask 최대 20%, 비교 총 3회(최초 1회 + repair 최대 2회)로 계산합니다. Lab LCP/CLS/TBT 또는 interaction과 field Web Vitals/미가용 사유도 기록합니다.
5. **Independent reviews:** `functional-reviewer`와 `design-reviewer`가 같은 immutable packet을 독립 판정합니다.
6. **Report / publish:** packet에 묶인 `pr-report-v2.1` JSON과 Markdown의 15개 섹션을 만든 뒤 draft PR을 발행합니다.

각 보고서 섹션은 `complete`, `not-run`, `blocked`, `not-applicable` 중 하나입니다. 현재 review packet에 속하지 않는 stale path는 PR에서 생략합니다. GitHub 이미지·diff·overlay는 실행별 branch가 아니라 단일 관리 branch `spec-to-pr/evidence`의 immutable 경로에 올리고 upload commit SHA로 고정합니다.

## 실행 정책: stage, agent, skill, tool

| Durable stage       | 이 케이스의 정확한 동작                                                                                                |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `intake`            | `briefPath`, 요청, scope, publication을 정규화하고 workload와 `requiredValidations`를 고정합니다.                      |
| `contracts`         | brief 수용 조건과 optional source의 우선순위·충돌·추적표를 확정합니다.                                                 |
| `implementation`    | 한 명의 implementation writer가 한 `implementationContextId`에서 구현합니다. API-backed UI는 `api-ready`가 먼저입니다. |
| `functional-review` | read-only `functional-reviewer`가 immutable packet으로 계약·diff·focused check를 판정합니다.                           |
| `design-review`     | UI scope일 때만 read-only `design-reviewer`가 판정하고, non-UI면 not applicable입니다.                                 |
| `report`            | `pr-report-v2.1` 15개 섹션에 source, API gap, visual ratio/assets, Web Vitals, review, risk, rollback을 기록합니다.    |
| `publish`           | `publication: draft`이며 ready일 때만 같은 source/target의 draft PR/MR을 생성·갱신합니다.                              |
| `archive`           | merge 뒤 authoritative evidence와 별도 사용자 요청이 있을 때만 실행합니다.                                             |

Agent 정책은 XS/S read-only scout 0명, M 최대 1명, L/XL 최대 2명입니다. Scout는 독립적인 read-heavy 탐색만 하고 구현을 편집하지 않습니다. L/XL의 functional/design reviewer만 구현 뒤 병렬일 수 있으며 **no nesting**, **parallel writer 금지**입니다.

- `stageSkillRoute`: public action은 `intake-contracts` → `implement` → `review-functional` 순서이며 UI면 `review-design`, draft면 `publish`로 이어집니다. 이 routing은 `deliveryProfile.recommendedSkills`가 아닙니다.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; 감지된 React/Next package → `react-best-practices`, `next-best-practices` optional candidate입니다.
- Brief UI라는 이유만으로 `playwright`를 추천하지 않습니다. `mode: feature` + UI mapping만 해당 candidate를 추가합니다.
- `appliedSkills`: `recommendedSkills`와 사용자가 준 `skillHints` 중 실제로 설치되어 available/applicable한 optional skill의 허용 합집합만 기록합니다. Missing optional skills는 blocker가 아닙니다.
- **workflow MCP:** Run/status/submission/publication에 필수. **Figma host:** `figmaUrl`을 줬을 때만 필수. **Playwright Test/CLI:** brief의 `requiredValidations`에 browser acceptance가 있을 때만 assertion과 structured result의 oracle로 사용하며 feature E2E나 영상은 자동 요구하지 않습니다.
- **Browser MCP:** 가능한 host에서 interactive reproduction/inspection에만 optional. **Chrome DevTools MCP:** console, network, performance, memory, live DOM 진단이 필요할 때만 conditional이며 screenshot/trace는 assertion을 대신하지 않습니다.

정상/blocked 모두 같은 `pr-report-v2.1` 15개 섹션을 씁니다. Blocked PR은 성공처럼 보이지 않게 멈춘 stage, 완료 작업, 미실행 검증, exact unblock action을 표시합니다.

### Ready, blocked diagnostic, resume

정상 경로는 `workflow_publish intent: ready`가 evidence-backed draft를 만듭니다. Blocker가 생기면 typed `blockerDetails`와 exact unblock action을 남기고, publication preflight가 허용할 때만 `workflow_publish intent: blocked-diagnostic`으로 diagnostic draft를 만듭니다. 이 draft는 계속 `status: blocked`이며 report/publish 통과가 아닙니다. Clean tree, non-target branch, 인증, 지원 remote, committed delta, target보다 한 commit ahead 중 하나라도 없거나 `PUBLISH_NO_DELTA`면 empty commit/issue fallback을 만들지 않고 **local blocked report**를 반환합니다.

`diagnostic-publication-uncertain`이면 자동 재발행하지 않습니다. GitHub/GitLab에서 matching draft를 확인해 사용자에게 보여주고, 명시적 승인을 받은 경우에만 같은 `workflow_publish`를 `recoverUncertain: true`로 호출합니다.

해결 뒤에는 **same Run**을 `workflow_status`/`resumeContext`에서 이어가 이미 통과한 stage를 반복하지 않습니다. Diagnostic draft가 있었다면 같은 source/target의 **same draft PR**을 `[Blocked]` 제목과 blocked label에서 정상 `intent: ready` 제목/본문으로 갱신하고 blocked label을 제거합니다.

## 증거와 검증 <span id="evidence-brief"></span>

다음은 **예상 예시** 경로입니다.

| 증거       | 예상 예시                                              | 통과 기준                                                                      |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 수용 조건  | `evidence/contracts/brief-acceptance.json`             | 각 조건이 구현·검사와 연결됨                                                   |
| API-ready  | `evidence/api/contract-test.json`                      | API scope일 때 `status: passed`, 실제 artifact, 같은 `implementationContextId` |
| 관련 검사  | `evidence/tests/focused-checks.json`                   | 적용 가능한 명령이 성공하고 skip/empty가 아님                                  |
| Figma      | `evidence/figma/figma-bundle.json`                     | URL을 줬을 때 connected-host provenance와 실제 PNG                             |
| 시각 비교  | `evidence/visual/checkout-report.json`                 | Figma/결과 exact·review ratio ≥ 98%, diff/overlay 존재                         |
| API gap    | `evidence/api/coverage.json`                           | 모든 operation의 production/mock/test 매핑 또는 명시적 blocker                 |
| Web Vitals | `evidence/performance/checkout.json`                   | lab budget과 field source 또는 unavailable reason                              |
| 리뷰       | `evidence/reviews/functional.json`, UI면 `design.json` | 독립 verdict가 approved                                                        |

기획서 모드는 targeted feature 영상이 자동 요구되지 않습니다. 필요한 검사는 기획서 범위와 저장소의 실제 스크립트로 정합니다.

## 예상 브랜치와 커밋 <span id="branch-and-commits-brief"></span>

- 브랜치 예상 예시: `codex/checkout-brief`
- 커밋 예상 예시: `feat: implement checkout acceptance criteria`
- 발행 전 조건: target 브랜치가 아닌 committed source branch, 의도한 변경만 포함, clean tree, target보다 최소 한 커밋 앞섬
- SpecToPR은 merge, approve, close, ready 전환을 하지 않습니다.

## 예상 Draft PR <span id="expected-pr-brief"></span>

**예상 예시 제목:** `feat: implement checkout from approved brief`

```md
## Accepted requirements

- AC-1 결제 수단 선택 → src/features/checkout/PaymentMethod.tsx
- AC-2 실패 상태 표시 → tests/checkout/error-state.test.tsx

## Implementation

- API contract와 mock을 추가하고 같은 implementationContextId에서 UI 연결

## Validation and reviews

- pnpm test -- checkout: passed
- functional-reviewer: approved
- design-reviewer: approved (UI scope)

## Evidence and risks

- evidence/contracts/brief-acceptance.json
- Figma review match: 98.74% (baseline / target / diff / overlay)
- API gap: none; documented operations 6/6 covered
- Web Vitals: LCP 2.1s, CLS 0.04, TBT 120ms
- 알려진 위험과 제외 범위
```

## Run이 멈추는 경우 <span id="blockers-brief"></span>

| 중단 원인                           | 사용자가 할 일                                     |
| ----------------------------------- | -------------------------------------------------- |
| 기획서/Figma/OpenAPI 중 하나가 없음 | 세 source를 모두 제공하거나 케이스를 다시 선택     |
| 기획서와 Figma/OpenAPI/요청이 충돌  | 어떤 source가 우선인지 결정하고 수용 조건 수정     |
| 필수 project guidance 누락          | `guidancePaths`의 실제 파일을 추가하거나 경로 수정 |
| reviewer가 changes requested        | 지적된 계약·구현·증거를 보완한 뒤 재검토 요청      |
| dirty tree 또는 source commit 없음  | 의도한 변경만 커밋하고 clean tree를 만든 뒤 재개   |

## 이 케이스가 하지 않는 것 <span id="exclusions-brief"></span>

- 기획서 밖의 endpoint, 화면, migration을 임의로 만들지 않습니다.
- 기능 개발 모드 전용 targeted E2E와 영상 하나를 자동으로 추가하지 않습니다.
- 토큰 압박을 이유로 필수 검증을 삭제하지 않습니다.
