## 이 사용법을 쓰는 경우 <span id="use-this-case-brief"></span>

기획서·Figma·API 문서를 한 번에 주고 화면과 API를 끝까지 구현한 초안 PR을 받고 싶을 때 사용합니다. 단순히 기획서를 요약하는 작업이 아니라 실제 구현과 검증까지 진행합니다. 기능 전체 E2E와 영상은 제외하지만 Figma 대비 화면 일치율, API 사용·누락 현황, Web Vitals는 필수입니다.

:::tip[입력 / 결과]
**입력:** 대상 저장소 + 기획서(PDF/MD 등) + Figma URL + OpenAPI 경로/URL · **결과:** 요구사항 충족표, 수치화된 화면 비교, 제외 범위와 API Gap이 있는 Brief 초안 PR
:::

## 반드시 제공할 것 <span id="required-inputs-brief"></span>

| 입력          | 요구사항                                                         |
| ------------- | ---------------------------------------------------------------- |
| 저장소        | 절대 경로이며 Git 저장소여야 합니다. 예: `/absolute/path/to/app` |
| `mode`        | `brief`                                                          |
| `briefPath`   | PDF/MD 등 실제 기획서 파일. 예: `docs/checkout.pdf`              |
| `figmaUrl`    | 구현할 파일/노드 URL. 실제 기준 PNG를 수집합니다.                |
| OpenAPI       | `openApiPaths` 또는 HTTPS `openApiUrls` 중 하나 이상             |
| 요청          | “구현해줘”만 쓰지 말고 어떤 수용 조건을 납품할지 적습니다.       |
| `changeKind`  | 실제 변경에 맞는 `feature`, `fix`, `refactor`, `docs` 등         |
| `publication` | PR까지 원하면 `draft`; 구현·검토까지만이면 `none`                |

## 선택 입력 <span id="optional-inputs-brief"></span>

- `scope: ui`: 이 케이스의 기본 UI 계약을 명시합니다.
- `docsPaths`: 비즈니스 규칙, 오류 사례, 분석 문서 같은 보조 자료입니다.
- `guidancePaths`: `AGENTS.md`, 구조 문서, 폴더 구성 문서 같은 프로젝트 지침을 명시합니다.
- `skillHints`: 설치되어 있고 현재 작업에 맞는 스킬을 요청합니다. 선택 스킬이 없어도 실행을 중단하지 않습니다.

```text
API 계약 자료를 먼저 만든 뒤 같은 구현 맥락에서 UI를 구현하고 관련 검사만 실행해.
```

## SpecToPR이 진행하는 과정 <span id="process-brief"></span>

1. **접수:** 경로와 발행 의도를 정리하고 예상 작업량, 토큰 범위, 신뢰도를 보여 줍니다.
2. **계약 확정:** 원본 해시가 있는 `sourceProvenance`, 수용 조건, API 작업, Figma `visualTargets`를 고정합니다.
3. **구현:** 같은 `implementationContextId`에서 확인된 API 타입·스키마·호출 모듈·모의 응답·계약 테스트를 만들고 UI를 연결합니다. 메서드·body·인증·binding이 불명확하면 안전하지 않은 쓰기를 만들지 않고 **API Gap**으로 남기며, 확인된 UI·상태·라우트 구현은 계속합니다.
4. **화면 비교 및 성능 측정:** 같은 경로·상태·테스트 데이터·화면 크기에서 Figma PNG와 결과 화면을 `compare-visuals`로 비교합니다. 각 결과 화면에는 기준과 같은 조건, 자료 제공자, ISO 형식의 촬영 시각, PNG 경로, `sha256:` 해시를 기록합니다. 실행 엔진은 비교 조건이나 해시가 달라지면 시도 횟수를 소비하지 않고 거부하며 정확 일치율·검토 일치율·차이 이미지·겹침 이미지를 계산합니다. 고정 기준은 일치율 92% 이상, 근거가 있는 마스킹 영역 20% 이하입니다. 최초 비교와 보정 후 최대 2회를 자동으로 수행하며 세 번째 유효 실패는 실패 이미지를 **화면 비교 Gap**으로 보존합니다. 집중 UI 검증은 전체 점수와 별도로 판정합니다. 실험실 LCP·CLS·TBT 또는 상호작용 지표와 현장 Web Vitals도 기록하고, 수집할 수 없으면 그 이유를 남깁니다.
5. **독립 검토:** `functional-reviewer`와 `design-reviewer`가 변경할 수 없는 동일한 검토 묶음을 각각 판정합니다.
6. **보고서 및 발행:** Brief delivery 본문에 요구사항 충족표, 제외 범위, 화면 비교와 상단 Gap을 정리한 뒤 초안 PR을 발행합니다.

각 보고서 섹션은 `complete`, `not-run`, `blocked`, `not-applicable` 중 하나입니다. 현재 검토 묶음에 속하지 않는 이전 검증 자료는 PR에서 제외합니다. 초안 PR에는 Figma 기준·결과·차이 이미지와 일치율을 제공합니다. GitHub용 이미지는 실행마다 새 브랜치를 만들지 않고 관리 브랜치 `spec-to-pr/evidence`의 변경되지 않는 경로에 올린 뒤 업로드 커밋 SHA로 고정합니다.

## 단계와 작업 담당

| 단계                | 이 방식에서 수행하는 작업                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| `intake`            | `briefPath`, 요청, 범위, 발행 방식을 정리하고 예상 작업량과 `requiredValidations`를 고정합니다.        |
| `contracts`         | 기획서 수용 조건과 선택 자료의 우선순위·충돌·추적표를 확정합니다.                                      |
| `implementation`    | 한 명의 구현 담당자가 하나의 `implementationContextId`에서 구현하며, 미확정 API는 Gap으로 남깁니다.    |
| `functional-review` | 읽기 전용 `functional-reviewer`가 검토 묶음으로 계약, 코드 차이, 관련 검사를 판정합니다.               |
| `design-review`     | UI 범위일 때만 읽기 전용 `design-reviewer`가 판정하며, 비-UI 작업에는 적용하지 않습니다.               |
| `report`            | 요구사항 충족표, 제외 범위, 화면 비교와 상단 Gap을 리뷰어 우선 본문으로 만듭니다.                      |
| `publish`           | `publication: draft`이면 Gap·실패·미실행 증빙이 있어도 같은 소스·대상의 초안 PR/MR을 만들 수 있습니다. |
| `archive`           | 병합 근거가 있고 사용자가 별도로 요청한 경우에만 실행합니다.                                           |

작업량이 XS/S이면 별도 조사 담당자를 두지 않고, M이면 최대 1명, L/XL이면 최대 2명의 읽기 전용 조사 담당자를 둘 수 있습니다. 조사 담당자는 서로 겹치지 않는 코드 탐색만 하고 구현을 편집하지 않습니다. 중첩 위임과 여러 구현 담당자의 동시 편집은 허용하지 않습니다. UI 구현이 끝나면 작업량과 관계없이 기능·디자인 검토를 같은 고정 묶음에서 동시에 진행합니다.

<details>
<summary>스킬과 도구의 세부 규칙</summary>

- `stageSkillRoute`: 공개 작업은 `intake-contracts` → `implement` → `review-functional` 순서로 진행합니다. UI 작업이면 `review-design`, 초안 발행이면 `publish`가 이어집니다. 이 경로는 `deliveryProfile.recommendedSkills`와 다릅니다.
- `recommendedSkills`: `figmaUrl` → `figma`, `design-system`; `openApiPaths` → `api-generator`; 감지된 React/Next 패키지 → `react-best-practices`, `next-best-practices`
- 기획서 기반 UI라는 이유만으로 `playwright`를 추천하지 않습니다. `mode: feature`이고 UI 연결이 있을 때만 후보에 추가합니다.
- `appliedSkills`: `recommendedSkills`와 사용자가 준 `skillHints` 중 실제로 설치되어 있고 현재 작업에 맞는 스킬만 기록합니다. 선택 스킬이 없어도 실행을 중단하지 않습니다.
- **워크플로 도구:** 실행 상태 조회, 자료 제출, 발행에 필수입니다. **Figma 호스트 기능:** `figmaUrl`을 제공한 경우에만 필수입니다. **Playwright Test/CLI:** `requiredValidations`에 브라우저 수용 검사가 있을 때 화면 상태 검증과 구조화 결과의 판정 기준으로 사용합니다. 기능 E2E나 영상은 자동으로 요구하지 않습니다.
- **Browser MCP:** 상호작용을 재현하고 살펴볼 때 선택적으로 사용합니다. **Chrome DevTools MCP:** 콘솔·네트워크·성능·메모리·실시간 DOM 문제를 진단할 때만 사용합니다. 스크린샷이나 추적 기록은 검증을 대신하지 않습니다.

</details>

기계용 보고서는 증거를 보존하지만, Draft PR 본문은 요구사항 충족표·제외 범위·화면 비교와 상단 Gap만 보여 줍니다. 내부 로그·Run ID·빈 체크리스트는 기본 본문에 넣지 않습니다.

### 정상 발행, 차단 진단, 재개

`workflow_publish`는 코드 변경과 발행 사전 조건이 있으면 API Gap·화면 비교 실패·미실행 검토가 있어도 Draft를 만들 수 있습니다. 그 Draft는 상단에 영향과 리뷰어 결정을 표시하며 verified나 merge-ready가 아닙니다. 작업 트리·브랜치·인증·원격 저장소·커밋 차이 조건 중 하나라도 맞지 않거나 `PUBLISH_NO_DELTA`이면 빈 커밋이나 대체 이슈를 만들지 않고 **로컬 보고서**를 반환합니다.

`diagnostic-publication-uncertain`이면 자동으로 다시 발행하지 않습니다. GitHub/GitLab에서 소스와 대상 브랜치가 같은 기존 초안을 확인해 사용자에게 보여 주고, 명시적인 승인을 받은 경우에만 같은 `workflow_publish`를 `recoverUncertain: true`로 호출합니다.

문제를 해결한 뒤에는 `workflow_status`와 `resumeContext`에서 **같은 실행**을 이어가 이미 통과한 단계를 반복하지 않습니다. 진단용 초안이 있었다면 소스와 대상 브랜치가 같은 **기존 초안 PR**의 `[Blocked]` 제목과 차단 라벨을 정상 `intent: ready` 제목·본문으로 바꾸고 라벨을 제거합니다.

## 검증 자료와 통과 기준 <span id="evidence-brief"></span>

다음은 **예상 예시** 경로입니다.

| 검증 자료  | 예상 예시                                              | 통과 기준                                                                |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| 수용 조건  | `evidence/contracts/brief-acceptance.json`             | 각 조건이 구현·검사와 연결됨                                             |
| API 준비   | `evidence/api/contract-test.json`                      | API 작업이면 `status: passed`, 실제 파일, 같은 `implementationContextId` |
| 관련 검사  | `evidence/tests/focused-checks.json`                   | 적용 가능한 명령이 성공하고 건너뛰거나 빈 결과가 아님                    |
| Figma      | `evidence/figma/figma-bundle.json`                     | URL을 제공했다면 연결된 호스트의 출처 정보와 실제 PNG가 있음             |
| 화면 비교  | `evidence/visual/checkout-report.json`                 | Figma와 결과 화면의 검토 일치율이 92% 이상이고 차이·겹침 이미지가 있음   |
| API 현황   | `evidence/api/coverage.json`                           | 모든 API 작업이 실제 호출·모의 응답·테스트에 연결되거나 차단 사유가 있음 |
| Web Vitals | `evidence/performance/checkout.json`                   | 실험실 기준과 현장 자료 또는 수집하지 못한 이유가 있음                   |
| 독립 검토  | `evidence/reviews/functional.json`, UI면 `design.json` | 적용 가능한 독립 판정이 모두 승인됨                                      |

기획서 방식은 변경 기능 영상이 자동으로 필요하지 않습니다. 필요한 검사는 기획서 범위와 저장소의 실제 스크립트로 정합니다.

## 예상 브랜치와 커밋 <span id="branch-and-commits-brief"></span>

- 브랜치 예상 예시: `codex/checkout-brief`
- 커밋 예상 예시: `feat: implement checkout acceptance criteria`
- 발행 전 조건: 대상이 아닌 소스 브랜치, 커밋한 변경, 깨끗한 작업 트리, 대상보다 최소 한 커밋 앞선 상태
- SpecToPR은 병합, 승인, 닫기, 검토 준비 상태 전환을 하지 않습니다.

## 예상 초안 PR <span id="expected-pr-brief"></span>

**예상 예시 제목:** `feat: implement checkout from approved brief`

```md
## 승인된 요구사항

- AC-1 결제 수단 선택 → src/features/checkout/PaymentMethod.tsx
- AC-2 실패 상태 표시 → tests/checkout/error-state.test.tsx

## 구현

- API 계약과 모의 응답을 추가하고 같은 implementationContextId에서 UI 연결

## 검증과 독립 검토

- pnpm test -- checkout: passed
- functional-reviewer: approved
- design-reviewer: approved (UI 작업)

## 검증 자료와 위험

- evidence/contracts/brief-acceptance.json
- Figma 검토 일치율: 98.74% (기준 / 결과 / 차이)
- API 누락: 없음, 문서화된 작업 6/6 검증
- Web Vitals: LCP 2.1s, CLS 0.04, TBT 120ms
- 알려진 위험과 제외 범위
```

## 실행이 멈추는 경우 <span id="blockers-brief"></span>

| 중단 원인                            | 사용자가 할 일                                       |
| ------------------------------------ | ---------------------------------------------------- |
| 기획서/Figma/OpenAPI 중 하나가 없음  | 세 입력 자료를 모두 제공하거나 사용 방식을 다시 선택 |
| 기획서와 Figma/OpenAPI/요청이 충돌   | 어떤 자료가 우선인지 결정하고 수용 조건 수정         |
| 필수 프로젝트 지침 누락              | `guidancePaths`의 실제 파일을 추가하거나 경로 수정   |
| 검토자가 수정을 요청함               | 지적된 계약·구현·검증 자료를 보완한 뒤 재검토 요청   |
| 작업 트리가 지저분하거나 커밋이 없음 | 의도한 변경만 커밋하고 작업 트리를 정리한 뒤 재개    |
