`brief`는 기획서를 읽어 사용자 기능과 완료 조건을 구현할 때 사용합니다.

## 입력

```yaml
case: brief
projectRoot: /absolute/path/to/project
briefPath: docs/payment-method.md
apiDocsPaths:
  - docs/payment-api.yaml
request: 결제 수단 선택 기능을 구현해줘
figmaUrl: https://www.figma.com/design/FILE/payment
test: on
```

`figmaUrl`과 `apiDocsPaths`는 선택 사항입니다. 제공되면 기획서와 함께 OpenSpec 문서에 반영합니다. Figma가 없다면 기획서의 승인된 화면 또는 기존 프로젝트 패턴을 사용하고, 숫자 비교 기준이 없다면 Gap에 남깁니다.

## 구현 전에 OpenSpec 문서를 준비합니다

`brief`는 바로 코드를 쓰지 않습니다. 대상 프로젝트의 OpenSpec 규칙을 먼저 확인하고, 없으면 다음 최소 구조로 변경 문서를 만듭니다.

```text
openspec/changes/<변경명>/
├── proposal.md
├── tasks.md
└── specs/<기능명>/spec.md
```

- `proposal.md`에는 목적, 범위, 기획서·API 문서·Figma 출처, 미확정 항목을 적습니다.
- `spec.md`에는 요구사항과 수용 시나리오를 적습니다.
- `tasks.md`에는 구현·테스트·화면 비교 작업을 적습니다.

## 자료와 OpenSpec 대조

기획서의 완료 조건, API 문서의 method·path·제약, Figma의 화면·상태·상호작용을 OpenSpec 문서의 요구사항과 한 항목씩 대조합니다. 자료에 있는데 OpenSpec에 빠진 내용은 문서를 보완한 뒤 다시 대조합니다.

자료 자체가 비어 있거나 서로 충돌하면 내용을 추측하지 않습니다. `proposal.md`의 미확정 항목과 Draft PR의 Gap에 영향·다음 작업을 기록합니다. 이 과정은 별도 Run이나 고정 리뷰어가 아니라, 구현 전 문서 정리입니다.

## 구현 규칙

- 기획서에서 실제 사용자 행동과 완료 조건을 먼저 정리합니다.
- UI는 사내 디자인 시스템과 기존 컴포넌트를 우선 사용합니다.
- 제공된 API 문서가 있다면 실제 사용한 method·path·목적만 PR에 기록합니다.
- 비어 있는 정책이나 API 정보는 임의로 채우지 않고 Gap으로 남깁니다.

## test: on | off

`test`를 생략하면 `off`입니다. `test: on`이면 확정된 OpenSpec 요구사항과 수용 시나리오마다 관련 실패 테스트를 먼저 작성하고, 최소 구현으로 통과시킨 뒤 리팩터링합니다. 대상 프로젝트의 기존 테스트 도구만 사용합니다.

`test: off`이면 이 변경을 위한 단위·통합 테스트를 새로 만들거나 실행하지 않습니다. `test: on`인데 기존 테스트 도구가 없거나 시나리오를 테스트로 만들 수 없으면 TDD를 한 것처럼 쓰지 않고 Gap에 남깁니다.

자료가 넓거나 충돌할 때만 읽기 전용 서브에이전트에게 자료·OpenSpec 대조를 맡길 수 있습니다. 주 작업자가 문서 수정과 구현을 맡고, 작은 요청은 주 작업자가 직접 대조합니다.

## PR에서 확인할 것

| 항목        | 작성 방법                                               |
| ----------- | ------------------------------------------------------- |
| 개발한 기능 | 기획서 문장이 아니라 구현된 사용자 행동을 한국어로 작성 |
| 화면 일치율 | Figma·승인 화면이 있을 때만 실제 비교 결과를 기록       |
| 사용한 API  | 변경된 호출만 method, path, 목적과 함께 기록            |
| Gap         | 기획 확인이 필요한 정책과 영향, 다음 작업 기록          |
| OpenSpec    | 변경 문서가 기획·API·Figma와 대조됐는지 검증에 기록     |

## 예시 Gap

| 확인이 필요한 내용         | 영향 | 다음 작업                   |
| -------------------------- | ---- | --------------------------- |
| 결제 수단별 노출 순서 정책 | 중간 | 기획 확인 후 정렬 규칙 반영 |

## PR 예시

```md
# [기획서 기반 개발] 결제 수단 선택

> Draft PR · 화면 96.40% · Gap 1개

## 개발한 기능

- 저장된 카드와 새 카드 입력 방식 중 하나를 선택해 결제할 수 있습니다.

## 화면 일치율

| 화면 | 비교 기준 | 비교 횟수 | 일치율 | 결과 | 증빙 |
| 결제 수단 기본 상태 | 승인 화면 | 1/3 | 96.40% | 통과 | 기준 · 구현 · Diff |

## 사용한 API

| Method | Path | 사용 목적 |
| GET | /payment-methods | 저장된 결제 수단 조회 |

## Gap

| 확인 또는 개발이 필요한 내용 | 영향 | 다음 작업 |
| 결제 수단별 노출 순서 정책 | 중간 | 기획 확인 후 정렬 규칙 반영 |

## 검증

- OpenSpec 문서와 기획서·API 문서·Figma 대조 완료
- `test: on` — OpenSpec 수용 시나리오 기반 단위·통합 테스트 통과
```
