가장 작은 `feature` 케이스로 전체 흐름을 확인해 보겠습니다.

## 1. 요청을 보냅니다

```yaml
case: feature
projectRoot: /absolute/path/to/project
request: 설정 화면에 알림 수신 토글을 추가해줘
targetBranch: main
test: on
```

`feature`는 요청만으로 시작할 수 있습니다. Figma URL이나 API 문서가 있다면 함께 주면 됩니다. 먼저 기능 요청을 OpenSpec 변경 문서로 정리·대조합니다. `test`를 생략하면 `off`이고, 이 예시처럼 `on`이면 OpenSpec 수용 시나리오로 TDD를 합니다.

## 2. 모델이 구현합니다

모델은 대상 프로젝트의 지침과 기존 구조를 먼저 읽습니다. UI라면 설치된 사내 디자인 시스템과 기존 컴포넌트를 우선 사용하고, 직접 필요한 코드만 수정합니다.

GitLab remote라면 이 단계보다 먼저 `glab` 인증·프로젝트 접근·MR API 읽기 접근을 점검합니다. 막힌 상태라면 코드를 바꾸지 않고 [GitLab MR 사전 진단](./gitlab)의 해결 순서를 안내합니다.

## 3. 실제 결과를 확인합니다

- `test: on`이므로 OpenSpec 수용 시나리오의 실패 테스트부터 작성해 구현·통과·리팩터링합니다.
- `feature`라면 변경 기능만 고르는 E2E를 한 번 실행하고, 사용자 흐름 영상 한 개를 남깁니다.
- 실제 변경에서 사용한 API를 찾습니다.
- UI 기준 이미지가 있으면 구현 화면과 같은 크기로 비교합니다. 92% 미만이면 Diff를 보고 수정·재캡처·재비교하며, 최초 비교를 포함해 최대 3회까지 시도합니다.
- 확인하지 못한 내용은 Gap으로 적습니다.

## 4. Draft PR을 만듭니다

PR 본문에는 `개발한 기능`, `화면 일치율`, `사용한 API`, `Gap`, `검증`이 들어갑니다. `feature`에는 `E2E 영상`도 넣습니다. API가 없으면 `사용한 API 없음`, Gap이 없으면 `없음`을 명확히 적습니다.

다음에는 [케이스별 가이드](../usage/)에서 시작 자료에 맞는 방법을 선택하세요.
