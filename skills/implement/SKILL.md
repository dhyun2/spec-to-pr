# Implement

Use one implementation context for API and UI; do not split them into separate agents or worktrees.

1. Read `workflow_status` and confirm the `implement` action from `workflow_advance`.
2. Follow the accepted requirements and `guidanceTrace` in precedence order. Consume `deliveryProfile.recommendedSkills` plus requested `skillHints`; apply only installed and applicable candidates in the same writer context. Project guidance wins over generic skill advice, a missing optional skill never blocks implementation, and only actually applied skills belong in submitted evidence.
3. When the action says `requireApiReady: true`, implement and verify API types, schemas, generated clients or wrappers, mocks, and contract tests from documented evidence. Write each result as a real project-local artifact before starting UI work. Build exactly one operation record for every intake-pinned `openApiOperations` method/path; omitted or invented operations are rejected. Include types/refs, client symbols, mock handlers, contract evidence, readiness, and explicit gaps.
4. Submit `kind: api-ready`, `status: passed`, a stable `implementationContextId`, a summary, all paths in `artifactPaths`, `apiArtifacts` with nonempty `types`, `schemas`, `wrappers`, `mocks`, and `contractTests` arrays, and operation-aware `operations`. Categories must use distinct physical non-empty files; path, symlink, or hard-link aliases are rejected. `contractTests` points to a JSON result with `status: passed`. Wait until `workflow_status` exposes the checkpoint before UI evidence submission, then continue UI in the same context.
5. Implement UI against those wrappers and mocks. For `figma`, do not add real API work: realize every accepted Figma design mapping with the recorded design-system export, digest-bound canonical asset, token, and font evidence; do not reinterpret component names such as `Logo/Normal/nxplus_park` as CSS or filenames. Submit `mockDataEvidence` with a strict JSON manifest shaped as `{deterministic:true, fixtures:[{id,path,sha256}]}`. Every named fixture must be a separate JSON object/array, included in `artifactPaths`, bound by digest, and referenced by at least one visual target. Capture each route/state at its logical geometry using the exact named fixture. When the next action is `compare-visuals`, wait for the fixture, `document.fonts.ready`, all declared assets, and the final UI state including any transition; then write the PNG and strict `visual-capture-receipt-v2` under `visual/actual/<reviewPacketId>/`. Keep visual captures free of incidental keyboard focus styling; assert keyboard focus in a separate interaction assertion. Bind packet/head, target, route/state, capture kind, logical size/DPR, state-contract and fixture digests, Playwright/browser renderer lineage and environment, fonts/assets, actual path/digest/dimensions, and runner/normalizer versions. Also produce passing `baseline-isolation-v1` evidence and an immutable `ui-assertions-v1` report derived from an attached Playwright Test CLI observation artifact for every required focused geometry, style, accessibility, and action assertion. Never render a baseline inside product output, resize captures, alter product behavior solely to produce evidence, or calculate a verdict outside the runtime.
6. The fixed pass threshold is 92%. When a valid comparison is below it, follow only the returned `implementation-repair` action: inspect its failed target metrics and diff/overlay, modify and commit implementation, submit a fresh implementation packet, and recapture for that new packet. Complete the first two valid failures and their repairs automatically without asking the user; the third valid comparison is the terminal attempt. Do not resubmit a screenshot against the failed packet. Invalid acquisition evidence is corrected without consuming an attempt, and focused assertion failures remain blocking even when the aggregate score is at least 92%.
7. For a user-facing `feature` profile, use a stable `implementationContextId` and run one unchained Playwright invocation selected by a specific test file, `@tag`, or `--project` value. Never use `--list`, `--pass-with-no-tests`, or an unfiltered full-project E2E command. Write a strict project-local JSON `resultPath` containing only `status: passed`, `selector` exactly equal to `testSelector`, the same `implementationContextId`, and a positive `testCount`. Record exactly one structurally valid WebM or MP4 container with non-zero duration, up to 25 MB, and include `featureEvidence` with `scope: targeted-feature`, `testSelector`, `testCommand`, `resultPath`, and `videoPath`. Make recordings reviewer-readable: pause about 500–800 ms before and after each meaningful action, keep the clicked control visible, and let the resulting state settle before ending; do not add arbitrary long waits or change production transitions merely to make a recording look better.
8. Call `workflow_submit` once with an `implementation` result: status, summary, `apiReady`, conditional `implementationContextId`, `uiChanged`, changed files, artifact paths, conditional feature/mock evidence, operation-complete `apiCoverage`, implementation-time `legacyCoverage`, and mode-required `performanceEvidence`. Each API row maps an intake-pinned operation to production call sites, mock handlers, and structured executable evidence or a blocking gap. For legacy, replace every contracted `planned` row with current-packet `migrated` target files and passing executable evidence, or an intentional exclusion; the key set must match exactly. Legacy API candidates come from `legacyInventory.apiCandidates` plus optional OpenAPI enrichment. Preserve each candidate's environment origin and authenticated/default transport semantics by mapping them to existing target configuration and HTTP-client abstractions; do not implement only the normalized path or copy a legacy environment expression into a target with different conventions. When candidates exist, API-ready/coverage is required; when none exist, submit no invented operation and preserve the complete adapter/digest-bound empty-inventory result. A genuinely unresolved method/path returns the same-Run network-evidence action before implementation and is never guessed here. For brief, legacy, and feature, record measured lab LCP/CLS plus TBT or measured interaction and either authoritative field Web Vitals or an explicit unavailable reason; never label lab TBT as INP.
9. When `deliveryProfile.draftEvidenceBundle` exists, write final API/route/accessibility/performance result JSON, current screenshots, and visual-comparison summary below its stable feature root. Preserve only final reviewer-facing screenshots there; keep browser traces, raw logs, and transient `output/` files outside the committed bundle. Reuse the same path on a rerun, updating the manifest metadata in the new commit rather than creating a run-ID directory.

Playwright Test/CLI is the acceptance oracle. The browser MCP is optional interactive diagnosis; do not require it for a passing acceptance result. Use CDP only for console, network, performance, memory, or live-DOM diagnosis. Captured screenshots and video do not replace assertions. If required browser evidence cannot run because the browser or runtime is unavailable, report `BROWSER_NOT_RUN` as blocking evidence and stop before review.

Run the target project's focused checks while implementing and repairing: changed-feature unit/type checks plus the declared browser assertion. Reuse a commit-bound passing receipt during independent review; rerun a focused check only when its evidence is missing or the reviewed files changed. Do not run the **plugin-maintainer checks** from the `spec-to-pr` repository merely because this skill is installed: its `pnpm check`, `case4:check`, `reviewer-scheduling:check`, and `bench:runtime` commands validate the plugin release, not a user's target project. A target project may still require a command with the same name through its own guidance. Run its complete project validation once on the final intended target-project commit; for `figma`, do not add performance measurement or a feature video unless the delivery profile explicitly requires them.

An API-backed passed UI result requires the earlier `api-ready` submission and final `apiReady: true`; the boolean alone is not evidence. Brief, legacy, Figma, fix, refactor, migration, docs, and `auto` runs do not record feature video unless their delivery profile explicitly requires it. Missing, empty, skipped, or failed contract evidence blocks submission. Do not invent endpoints or report checks that did not run.

Keep implementation as one SDK action boundary. If the runner reaches 80% after this boundary, rely on the durable Run, contract artifacts, changed files, and test evidence in its compact checkpoint rather than replaying the full conversation. If the automatic hard limit is reached, stop before review or publication and return `split-required`; split the work into independently verifiable slices without trading away tests, review, or required gates.

Submit only portable project-relative, `/`-separated safe names in `artifactPaths`, API artifact arrays, `resultPath`, and `videoPath`. Reject absolute, traversal, control-character, backslash/non-portable, or secret-shaped paths, and never embed token, password, secret, or credential values; a descriptive name such as `token-validation.json` remains valid.
