# brief · feature OpenSpec 준비

`brief`와 `feature`는 구현 전에 대상 프로젝트의 `openspec/` 안에 변경 문서를 준비합니다. 이는 작업 상태를 저장하는 Run이 아니라, 구현 전에 합의할 요구사항 문서입니다. `figma`와 `legacy`는 이 문서를 만들지 않습니다.

## 1. 자료를 같은 변경으로 묶기

`brief`는 기획서, 제공된 API 문서, Figma URL, 프로젝트 지침을 읽습니다. `feature`는 기능 요청, 제공된 API 문서·Figma, 프로젝트 지침을 읽습니다. 변경 이름은 `kebab-case`로 정합니다. 기존 프로젝트가 OpenSpec 규칙이나 템플릿을 갖고 있으면 그것을 우선합니다. 없으면 아래 최소 구조를 만듭니다.

```text
openspec/changes/<change-name>/
├── proposal.md
├── tasks.md
└── specs/<capability>/spec.md
```

- `proposal.md`: 목적, 범위 안/밖, 자료 경로·URL, 미확정 항목
- `spec.md`: 구현해야 할 요구사항과 수용 시나리오
- `tasks.md`: 문서, 구현, 선택한 테스트, 화면 비교 작업

## 2. 자료와 스펙 대조하기

아래 항목을 각 케이스의 자료와 OpenSpec 문서에서 한 줄씩 대응합니다.

| 자료에서 확인할 것        | OpenSpec에 반드시 남길 것   |
| ------------------------- | --------------------------- |
| 사용자 목표와 완료 조건   | 요구사항과 수용 시나리오    |
| API method·path·오류·제약 | API 의존성 또는 미확정 항목 |
| Figma 화면·상태·상호작용  | 화면 상태와 완료 조건       |
| 범위 밖 정책·빈 정보      | `미확정 항목`과 PR Gap      |

기획서·기능 요청·API 문서에 있는 내용이 OpenSpec에 빠졌다면 OpenSpec을 고치고 다시 대조합니다. 반대로 자료 자체가 비어 있거나 서로 충돌하면 사실을 만들지 않습니다. `proposal.md`의 미확정 항목과 최종 PR의 Gap에 영향·다음 작업을 남깁니다.

## 3. test: on | off

`brief`와 `feature`의 `test`는 생략하면 `off`입니다.

- `test: on`: OpenSpec의 확정 요구사항과 수용 시나리오마다 테스트 항목을 적습니다. 먼저 관련 실패 테스트를 작성하고, 최소 구현으로 통과시킨 뒤 리팩터링합니다. `tasks.md`에는 `실패 테스트 → 구현 → 통과 → 리팩터링` 순서를 남깁니다. 대상 프로젝트의 기존 테스트 도구만 사용합니다.
- `test: off`: 이 변경을 위한 단위·통합 테스트를 새로 만들거나 실행하지 않습니다. `tasks.md`에서 TDD 작업을 넣지 않고, PR `검증`에는 `test: off — TDD 테스트 미작성·미실행`이라고 기록합니다.

`test: on`인데 기존 테스트 도구가 없거나 OpenSpec 시나리오를 테스트로 만들 수 없으면 테스트를 만들어 냈다고 쓰지 않습니다. 이유·영향·다음 작업을 Gap에 남깁니다. `feature`의 변경 기능 E2E와 영상은 TDD와 별개인 사용자 흐름 증빙입니다.

## 4. 구현을 시작하는 기준

확정된 요구사항, API, 화면 상태가 OpenSpec에 반영된 뒤 구현합니다. 미확정 항목은 안전한 범위의 구현을 막지 않지만, 인증된 변경 요청이나 정책을 추측해서 구현하지 않습니다.

자료가 많거나 충돌이 있을 때만 호스트가 지원하는 읽기 전용 서브에이전트에게 이 대조를 독립적으로 맡길 수 있습니다. 결과를 받은 주 작업자가 OpenSpec을 갱신하고 최종 판단합니다. 서브에이전트의 사용은 필수가 아니며, 새 Run·리뷰어·상태 저장을 만들지 않습니다.
